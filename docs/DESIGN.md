# Keel — Design

Status: Draft 9 · 2026-10-14 (retry efficiency: corrective turn, session resume, flake re-gate, no Sonnet-low tier) · Owner: Brett Stark

This file is the single source of truth: decision, requirements, architecture,
verification. The tests in `test/` name the requirement IDs they prove.
`BUI-` and `KEEL-` ids are internal tracker ids (Linear issues and `cards/`); they name where a rule came from.

## 1. Decision

Keel is the default way to build product cards (owner, 2026-10-04; the restart of the owner's earlier agent tooling that led
here is in git history). It is finished work, not a pilot: there is no kill date, no time or commit-share limit
(owner, 2026-10-06), and no rule that keeps it private. It is MIT-licensed and may be used, given away, or sold
(G11). The owner judges its value from `keel report --value` (§8), at any time. Scope stays small by rule
(`CLAUDE.md`): no scheduler, service, or orchestration features.

## 2. Goals and metrics

| ID  | Goal                                                  | Metric                                                                                                                                                                                                                       |
| --- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G1  | Fast                                                  | Median card → PR-ready ≤ 30 min (S/M). Gate ≤ 5 min p50.                                                                                                                                                                     |
| G2  | Token-efficient, **dynamic model/effort per attempt** | Tokens and human minutes per accepted card, Keel run vs native (`docs/PILOT.md`). Tier-0 pass share over all runs.                                                                                                           |
| G3  | Autonomous                                            | Under 5 % human interaction from idea to merged work, aim under 1 % (owner, 2026-10-12): agents file and build the work they find (REQ-LINEAR-22). Human only at §6.4 points. Measured as the human touch rate (REQ-LED-14). |
| G4  | **Built-in quality (the USP)**                        | 0 locked-file violations merged. Held-out tests pass for M/L. Human spot check: ≥ 8/10 new tests would fail without the fix. Mutation score optional.                                                                        |
| G5  | Policy-clean merges                                   | 0 bypass markers, 0 out-of-scope files, 0 unapproved test/verification edits at merge. ("Zero slop" is the aim; these are what is checked.)                                                                                  |
| G6  | Minimum docs, full trace                              | Every card has EARS requirements; every requirement has a test that names its ID.                                                                                                                                            |
| G8  | Provider-neutral                                      | Claude Code, Codex, or any CLI via the `exec` provider; config only.                                                                                                                                                         |
| G9  | Safe                                                  | Card text never reaches a shell; config from base; verification files locked; no push to main; Keel is not a sandbox (§6.5).                                                                                                 |

| G12 | **Any project**                                       | Any language, build system, or project type (app, library, CLI, infra, docs, monorepo) through configured commands. Presets via `keel init`. Gate proven on JS, Python, and Go fixtures.                                     |

## 3. Market position (checked 2026-09-25)

- Autonomy and speed are commodity: Claude Code background agents, Codex in
  Linear, Cursor cloud agents, Factory, Devin. OpenAI Symphony (Apache-2.0)
  orchestrates issues to agents.
- Native model switching exists but differs: Claude `opusplan` switches by
  phase; Factory routes subagents by complexity. Neither escalates on an
  independent gate result [review S07, S14].
- Closest prior art: **Probity / TDD Guard** (MIT) hooks agent edits and
  enforces TDD, partly with an AI validator. Keel differs by checking the
  finished commit with deterministic stages only.
- Review bots are models grading models; the Martian benchmark reports recall
  around 63 % of known issues (exact F1 range unverified).
- Claim Keel can defend: _"Agent patches keep an approved verification policy
  and produce reproducible before/after evidence."_ Not: "prevents bad AI code"
  or "proves tests were written first." Demand is unvalidated.

## 4. Principles

1. Do not build an agent, scheduler, or reviewer model. Drive existing CLIs.
2. Code decides pass/fail. A model never grades its own work.
3. Cheapest tier first. The gate result is the only escalation signal.
4. Tests first. The test must fail on the base code and pass on the head.
5. Existing tests are locked: not deleted, not skipped, not weakened.
6. One file of documentation per card (the card). Repo-level
   `docs/requirements.md` and `docs/architecture.md` are optional and short.
7. A mechanism stays only if the ledger shows it catches real problems.

## 5. Requirements (EARS)

Card and config

- **REQ-CARD-1** The card parser shall read `key: value` header lines (`kind`, `size`, `paths`, `heldOut`, `allowEdits`) before the first `## ` heading and keep the full markdown as the task text.
- **REQ-CARD-2** If `kind` or `size` is missing or invalid, a header key is unknown or given twice (a decoy `heldOut` once hid the real one, BUI-1189), or the card ID is not `[A-Za-z0-9._-]{1,64}`, then Keel shall reject the card.
- **REQ-CARD-3** A card file inside the repo shall be read from the base commit; a card missing there shall be rejected. Cards outside the repo are read from disk. Inside or outside is decided on real paths (symlinks resolved, true letter case), so an alias of the repo (`/var` for `/private/var`, `~/projects` for `~/Projects`) is still inside.
- **REQ-CARD-4** A card may list `acceptance`: comma-separated names, each matching `[A-Za-z0-9_-]+`. A name selects a command from `keel.json`; the card never supplies a command.
- **REQ-CFG-1** Keel shall read `keel.json` from a git ref — the base commit for the gate — merge it over defaults, and reject unknown keys and invalid values (empty checks, no tiers, bad tier indexes, and every key of the wrong type or range: `checks` not a table, a tier provider other than claude, codex, or exec, `workerTimeoutSec` not an integer ≥ 1, `failureTailChars` not an integer ≥ 0, `workerArgs` not a table of string arrays, a list key with a non-string entry, `heldOutRequired` outside S, M, L). `startTier` merges over its default floors, so a partial table keeps the others, and an unknown `startTier` key is rejected: a partial table once made an infra card start at an undefined tier (BUI-1193). `checks` and `testCommand` have no default: a missing value is an error that points to `keel init`. `heldOutCommand` defaults to `testCommand`. `acceptance` is an optional table of name to command (REQ-GATE-15); `install` is an optional command run in fresh checkouts (REQ-GATE-16).

Gate (the USP). Trust model: the card, the base commit, and Keel itself are trusted; everything in base..head is not.

- **REQ-GATE-1** The gate shall run the configured checks in a fresh checkout of the committed head (shared dependency dirs linked) and stop at the first failing stage. Each temporary checkout is removed after its stage, including directories a check left read-only; a removal failure is reported on stderr and never replaces the stage result (on 2026-10-13 a read-only cache directory made the gate throw, losing the result and leaking the checkout).
- **REQ-GATE-2** If the working tree is dirty, then the gate shall fail before any check.
- **REQ-GATE-3** Where the kind is `bug` or `feature`, the gate shall prove counterfactual regression: the test command passes on a clean base; the added/changed test files overlaid on base, byte for byte and with their mode (a binary fixture is not re-encoded; an executable test stays executable), make it fail with a real test failure (not timeout, not exit 126/127) whose output names a new test file; and the test command passes on a fresh checkout of head (run separately unless a passing check already ran the same command). With no test change it shall fail. When the overlay passes and no new test file name appears in its output, the failure shall carry a hint that the test command may not run the new files (a runner that lists files by name). (This proves "fails before, passes after", not that tests were written first.)
- **REQ-GATE-4** If a test file existing at base is modified, deleted, or type-changed, a `verificationPaths` file (incl. `.gitattributes`) changes in any way, a file the configured commands run — directly or through the `package.json` scripts they invoke at any depth (a script that runs another script is followed, cycles end at the first repeat), incl. pre/post hooks (e.g. `node scripts/check.mjs`) — changes, `package.json` `scripts` change, or its test/lint/format tool keys (`jest`, `mocha`, `ava`, `c8`, `nyc`, `eslintConfig`, `eslintIgnore`, `prettier`) change, then the gate shall fail unless the card's `allowEdits` names the path. `verificationPaths`, runner files, and the `package.json`/`pyproject.toml` names match without regard to letter case, as a case-insensitive filesystem opens them (`PYTEST.INI` is `pytest.ini`). Test globs match exactly, as they are naming conventions (`*Test.java` is not `Latest.java`), and so do `allowEdits` and `paths`, so they never widen.
- **REQ-GATE-5** If a changed file at head is a symlink or submodule, then the gate shall fail. Git reads every path literally (`--literal-pathspecs`), so a file named like pathspec magic (`:evil`, `:(glob)x`) is still checked: on 2026-10-13 a symlink named `:evil` passed and `:!x` crashed the gate.
- **REQ-GATE-6** If added lines in a test file contain a skip or focus marker, then the gate shall fail with file and line.
- **REQ-GATE-7** Where the kind is `refactor`, `ui`, `infra`, or `chore`, the gate shall not require red proof; REQ-GATE-4 still applies.
- **REQ-GATE-8** Diff attributes shall not hide lines from the scanners (`--text --no-textconv`). If added lines contain a lint/type/hook bypass marker in a file not listed in `bypassAllow`, then the gate shall fail with file and line.
- **REQ-GATE-9** Where the card lists `paths`, if a changed file matches none of them, then the gate shall fail.
- **REQ-GATE-10** Where size is in `heldOutRequired` (default M, L) and kind is `bug`/`feature`, the card shall name an absolute `heldOut` directory. An empty directory fails. The gate shall add its files to checkouts without overwriting any file; the held-out command must pass on head and, for bug/feature, fail on base as a real test failure (this also proves the tests ran). The builder prompt shall not contain the held-out path, and failure feedback shall carry only the rule name. (A guardrail against accidental leakage, not an isolation boundary: the worker has the user's file access.)
- **REQ-GATE-11** The gate shall write a uniquely named JSON receipt with card, base SHA, head SHA, and each stage's result, and exit 0 only if all stages pass.
- **REQ-GATE-12** The gate shall refuse to write overlay or held-out files through symlinks or outside the temporary checkout, and shall create no directory before that check.
- **REQ-GATE-13** If HEAD moved or a _tracked_ file was modified during the checks, then the gate shall fail. New untracked files (build/test cache litter — `__pycache__`, `.pytest_cache`, `target/`, `node_modules/.cache`) shall not fail this check: they are normal tool output, not tampering.
- **REQ-GATE-14** Untracked or ignored files in the worker's worktree shall not affect the result (fresh checkout).
- **REQ-GATE-15** Where the card lists `acceptance` names, the gate shall run each named command from the base `keel.json` `acceptance` table on a fresh checkout of head, after the checks pass, with the same scrubbed environment as checks (REQ-RUN-12). A failing command fails the gate as stage `acceptance:<name>`. A name the base config does not define fails the gate as `unknown-acceptance` before anything runs. This makes a card's prose acceptance criteria executable without letting card text reach a shell.
- **REQ-GATE-16** Where `keel.json` sets `install`, the gate shall not link shared dependency directories into any fresh checkout (candidate, base for the red proof, held-out); it shall run `install` in each one first, with the scrubbed environment (REQ-RUN-12), reporting stage `install` for the candidate. A failing install fails the gate as `install-failed`. `keel run` shall not link shared directories into the worker worktree either, so a worker that changes dependencies installs its own. Rationale: symlinked `node_modules` make the checks test what the worker last installed, not what the committed manifest and lockfile produce (found 2026-09-30, BUI-1014). Without `install`, behavior is unchanged.
- **REQ-GATE-17** Where the caller gives a cache directory (`keel gate` and `keel run` do), a green base test run (REQ-GATE-3 baseline) shall be recorded per repository (git common dir, so every worktree of a repo shares it), base commit, test command, install command, linked directories, and UTC day, and a later gate with the same key shall skip that run. A red baseline is never recorded. Rationale: the 2026-10-03 pilot spent up to 35 min per qa-architect gate, a third of it re-proving the same unchanged base on every attempt.
- **REQ-GATE-18** When a configured check, the head regression run, an acceptance command, or the REQ-GATE-3 base baseline fails, the gate shall run the same command once more on the same checkout. A pass on that retry passes the stage marked `flaky`, keeps the first failure output in the receipt, and is shown by `keel gate` and logged and recorded (`flaky`) by `keel run`. A second failure fails the stage. Rationale: in the 2026-10-03 pilot two of six cards escalated to Opus because a test timed out under load on a head that then passed unchanged.
- **REQ-GATE-19** If base..head changes no file, the gate shall fail with rule `no-change` before any other stage. Rationale: in pilot round 2 a card already satisfied on main passed the gate with an empty diff, which would certify (and with `--pr` try to publish) no work.
- **REQ-GATE-20** Where `keel.json` sets `mutation` (a non-empty command; default none) and the kind is `bug` or `feature`, the gate shall, after every other stage passes, run it on a fresh checkout of head with `KEEL_CHANGED_FILES` set to the added or modified non-test files, newline-separated. A non-zero exit fails stage `mutation` (`mutants-survived`), and its output goes to the next attempt. With no such file the stage is skipped. Tools: StrykerJS (`--mutate`), mutmut (`--paths-to-mutate`), go-mutesting, cargo-mutants (`--file`), wrapped to read that variable. Rationale: red proof shows a new test fails on base, not that it is strong (finish list F3).
- **REQ-GATE-21** Unless `keel.json` sets `review: false` (default `true`), the gate shall end with stage `review`: the strongest tier whose family (`family`, else `provider`) differs from the builder's tier (with no builder, the strongest tier) reads the card and the diff on a fresh checkout of head and answers `FINDING <severity> <path>:<line> <text>` lines and one `VERDICT:` line. The stage fails only on findings at or above `reviewBlock` (`critical`, `high`, `medium` (default), `low`) that cite a changed file; others are notes in the PR body. A finding line may be a list item, use `**` or `__` emphasis on `FINDING` and the severity, or backticks, and cite `path:N`, `path:N-M` or `path:N:C`; the path is matched against the changed paths, longest first, so a path with a space or `__` (`pkg/__init__.py`) parses (BUI-1194: each of these forms once passed the gate silently). A `FINDING` line that still does not parse is kept as `unparsed` in the receipt and the stage line, never blocking and never dropped. No reviewer of another family fails `no-cross-reviewer`; a failed reviewer or no verdict fails closed (`review-unavailable`), and `keel run` stops rather than escalate. The review cost counts toward the card. Rationale: auto-merge needs tested and reviewed changes (§9, K1). Default on and blocking from `medium` since 2026-10-12: in one PR of the owner's private setup repo, 8 of 9 cross-model findings were real `medium` (P2) defects that every test and gate stage had passed.
- **REQ-GATE-22** When the reviewer is unavailable (quota, outage, no verdict) and `reviewFallback` is on (keel.json, default `true`), the review stage shall try every other tier in turn until one gives a verdict: tiers of another family than the unavailable reviewer first, then the rest, each group strongest first. That review blocks like any other. The review result records `fallback: { from, status }`, plus `tried` (the fallbacks that were out too) when there were any; the stage line and the `keel/gate` description name it. Only when every tier is unavailable does the stage stay `review-unavailable`, and its result lists the fallbacks that were out as `tried`; then `keel run` keeps the build (REQ-RUN-24) and the poll goes on to other issues (REQ-LINEAR-19). The review cost and usage count every reviewer that ran. Rationale: owner rule 2026-10-12, a provider quota must not stop the loop; one Codex quota stopped all merges for 9 hours. The fallback can share the builder's family, so it is weaker than a cross-family review; the receipt says so.
- **REQ-GATE-23** When an earlier receipt of the same card has a review (not unavailable) and its head is an ancestor of HEAD (HEAD itself counts), the review prompt shall add that review's blocking findings and the diff from its head to HEAD, and tell the reviewer to use medium or higher only for a previous finding that is not fixed or a defect in that change, and low for any other defect. The newest such receipt counts. Code still decides what blocks (`reviewBlock`); low findings become follow-ups (REQ-RUN-27). Rationale: each re-gate re-read the whole diff and blocked on new findings in unchanged text, so fixes did not converge (2026-10-12: one card reviewed 14 times; BUI-1147). Trust: receipts sit where candidate code could write; a forged one changes only the prompt, as the candidate's diff already can. A receipt that is not a regular file (a directory throws, a FIFO blocks), is not JSON, or has no commit SHA `head`, valid `at`, `results` list, or list of review problems, is skipped (a forged head must not reach git as an option; a receipt still being written must not stop the gate).
- **REQ-GATE-24** Keel shall record each review's token spend (uncached input, cache writes, output) per provider family in `review-spend.jsonl` in the state dir, so every session of the machine shares one count. Where `keel.json` sets `reviewWindows` (table of family to `{ hours, tokens }`; default none), the spend of the last `hours` is that family's window use. `keel gate` shall print the estimate of tokens left before it reviews; when the window is nearly used, the line names the fallback that reviews first, or says the reviewer still reviews and why: `reviewFallback is off`, `no fallback reviewer`, or `no fallback has room` (BUI-1157). When the reviewer's window has 10 % or less left, `reviewFallback` is on, and the fallback reviewer's window is not also that low, the review stage shall use the fallback reviewer first, naming `window nearly used` in `fallback.status`; the unused quota is not spent to the end. If that fallback is unavailable, the stage tries the reviewer. Rationale: one Codex window is shared by every session, and the loop failed on the quota instead of moving off it before the quota ran out (BUI-1153).
- **REQ-GATE-25** Where `keel.json` sets `lightReview` (`{ maxLines, effort }`; default 20 lines, `low`; `null` turns it off) and a re-gate (REQ-GATE-23) changes only `.md`, `.txt`, or `.rst` files since the previous review, by at most `maxLines` added plus deleted lines, the reviewer shall run at that effort instead of the tier's. The review result records the effort used. Rationale: a re-gate after a one-line doc fix re-read the full prompt at full effort (BUI-1153).
- **REQ-GATE-26** When a reviewer gives no verdict, the review result shall record it in `unavailable`, in the order tried: `reviewer`, `status` (`no verdict` when the worker exited cleanly without a verdict line), `retryAt` when its output names a reset time (Codex "try again at 10:09 AM", Claude "resets 3pm", "reset at 11:30 PM"; kept as written), and the last 500 characters of its output. The stage line and the `keel/gate` description name every reviewer that was out, with its status and reset time. Rationale: on 2026-10-13 the three Claude fallbacks failed within 3 seconds, the receipt kept only their labels, and the FAIL line showed only Codex's `quota`, so the cause could not be found (BUI-1161).
- **REQ-GATE-27** When a reviewer fails with `quota` and its family spent tokens in the last 5 hours (`review-spend.jsonl`, REQ-GATE-24), Keel shall record that spend as the family's learned limit in `review-limits.json` beside it (`{ hours: 5, tokens }`). With no `reviewWindows` entry for a family, its learned limit is its window (REQ-GATE-24), so the next gate whose family is nearly used goes to the fallback first; a `reviewWindows` entry overrides it. The window line marks a learned limit, and `keel doctor` prints one window line per reviewer family with a known window. Rationale: `reviewWindows` was empty everywhere, so the early switch never happened; Codex on a Plus plan ran out after about 20 reviews of about 93k tokens (BUI-1167).
- **REQ-GATE-28** `keel gate --wait-review <hours>`: when the review stage stays unavailable and a reviewer named a reset time (REQ-GATE-26) that is at most `hours` away (read as the next such local clock time, plus one minute), the gate shall print the wait, sleep until then, and run the review stage once more on the same head, in the same process; the other stages are not run again, and the receipt holds only the second review. No stored receipt is read, so candidate code cannot forge a pass by writing one. Rationale: a gate of a large repo took 10–15 minutes, and a full re-gate after each quota failure cost hours (BUI-1166).
- **REQ-GATE-29** `keel gate` and `keel run` shall run the stages that run project commands (checks and tests, red proof, held-out, mutation) only while holding one of a fixed number of machine-wide slots in `locks/` in the state dir: `KEEL_GATE_SLOTS`, else a number that follows the machine's idle CPU and memory (REQ-SLOT-1). Slots go first come, first served: each request leaves a ticket file there, and a gate takes a slot only while fewer live tickets are ahead of it than slots are free; a gate asks again for each stage, with the ticket time of its start (REQ-SLOT-3), and a ticket whose process is gone is removed. A gate that must wait prints `waiting for gate slot (N running of S)` (with `, M ahead` when gates are queued before it), again each time the line changes, and waits; the wait is outside every stage timeout. A slot is a directory taken with an atomic `mkdir` and holds its owner's pid; a slot whose owner is gone, or that has had no pid for a minute, is taken over, one gate at a time: under a `<slot>.takeover` lock (atomic `mkdir`; cleared after a minute if its gate died) the slot is removed only if it is still dead, and a gate frees its slot only while the slot still holds its pid. Without that, a gate that saw a slot dead removed it after another gate had taken it over, and two gates ran in one slot (BUI-1200). Rationale: parallel gates of one product repo pushed 160–270 s test suites past the 900 s timeout, and the failure read as a test failure (BUI-1169). Without the queue, a running gate retook its slot between stages at once, and gates polling for a slot waited over 50 minutes while newer gates passed (2026-10-13).
- **REQ-GATE-30** Before it gates, `keel gate` shall print a warning, and not block, (1) for each local or remote branch whose commits HEAD contains but base does not (except HEAD's own branch): `stacked on <branch> (N commits): merge <branch> first, or rebase onto <base>`; and (2) when the added plus deleted lines outside tests and prose exceed the card size budget (S 300, M 800, L 1500), naming the three files with the most changed lines. Rationale: five stacked size-L branches of one product repo each merged again with 9–18 conflicting files after every merge, and every review round of each found new medium findings (BUI-1168).
- **REQ-GATE-33** Where `keel.json` sets `testFilesCommand` (null by default; a command with a `{files}` placeholder, read from base like all policy), the red-proof overlay (REQ-GATE-3) shall run that command for the new test files only, instead of the whole `testCommand`. Each `{files}` becomes the proof files' paths, single-quoted for the shell; the paths come from git, never card text, and one that starts with `-` gets `./`. The base baseline still runs the whole `testCommand` (REQ-GATE-17). The red proof runs only the new files when two things hold on the head checkout (receipt row `targeted-on-head`, which never fails the gate): the whole `testCommand` output there names each new file, or the file matches a file glob that `node --test` gets in `testCommand` or in a `package.json` script it runs at any depth (`npm test` → `node --test test/*.test.js`; the value of an option such as `--test-coverage-include x` or `--import y` is not a glob, `--` ends the options, which options take a value is read from `node --help`, and an option it does not list right before a file word gives no globs; an unquoted `**` is the shell's and stays in one directory; none when a test filter `--test-name-pattern`, `--test-skip-pattern`, `--test-only`, or `--test-shard` or a `cd` is in any of them), else `unseen` lists them, so the suite, and CI, really runs it; and the files command passes on its first run (no REQ-GATE-18 retry: a flaky one is not trusted on base), so a runner that cannot take these files never yields a false "fails on base". Otherwise the red proof runs the whole suite as before, which fails a new test the suite never runs with `test-passes-on-base`. A runner whose passing output names no files (`pytest -q`) therefore gets no saving; `pytest` without `-q` names them. `keel init` proposes it from the kind that supplies `testCommand`: for vitest and jest (`<pm exec> <runner> {files}`), whose passing output names each file, and `node --test {files}` for a `node --test` test script with file globs; none for a bare `node --test` and mocha (they print test names, not files), `pytest -q` (dots only; plain `pytest` names files, so set both by hand), go, cargo, rake or `make test`. Rationale: on 2026-10-13 a product repo's gate ran the whole pytest suite three times (head, base, base with the new tests); the overlay only needs the new files. On 2026-10-17 keel's and another node --test repo's red proof took 4–10 minutes, because `node --test` names no files and the proof always ran the whole suite (BUI-1353).
- **REQ-GATE-34** The gate's temporary checkouts (REQ-GATE-1) shall be made in one `keel.noindex` directory under TMPDIR, never directly in TMPDIR, and each is removed after its stage. Rationale: macOS Spotlight skips a directory whose name ends in `.noindex`; on 2026-10-13 its indexers were busy with thousands of `keel-wt-*` checkouts while gates queued at a load average above 100.
- **REQ-GATE-40** The gate shall measure what the candidate changed (changed files, added lines, locked-file and `package.json` comparisons, the review diff) from the merge base of base and head, which is what a merge applies, so commits the base gained after the branch left it are never read as the candidate's changes. Policy (`keel.json`) is still read at the base, the red proof still runs on the base, and runner files called from either the merge base's or the base's `package.json` scripts stay locked (REQ-GATE-4), so a script the base added after the branch left cannot point at a file the branch changed. Rationale: on 2026-10-13, branches behind main failed as `existing-test-changed` for tests main had added, and each needed a merge and a second gate.
- **REQ-GATE-41** The review parser shall also accept `FINDING info <path>:<line> <text>`. An `info` finding never blocks, whatever `reviewBlock` is; it is a note (REQ-GATE-21), so it reaches REQ-RUN-36 and REQ-RUN-27 like a low one. Before, such a line was kept only as unparsed.
- **REQ-GATE-42** When the root `package.json` `scripts` change (REQ-GATE-4), the gate shall not lock the file if the change is append-only: the same script names; every changed script is one `testCommand` runs (followed through `npm run` and pre/post hooks as REQ-GATE-4 does); its new text is its old text plus whitespace-separated arguments (text glued to the old last argument, as in `test/a.test.jstest/b.test.js`, changes that argument and stays locked), each a path or glob (optionally quoted, no shell syntax, no leading `-`) that matches `testGlobs`; and its old text already ends with such an argument. Any removal, reordering, flag, shell operator, non-test path, new or removed script, script `testCommand` does not run, or nested `package.json` stays locked with a `why`. The `locked` result lists the edit in `relaxed` with its proof. Rationale: a runner that already lists test files can only gain files, and each added file is a test by the repo's own definition, which an existing glob could already run; a runner that discovered every test (`node --test`, `vitest run`) would be narrowed by a first file argument, so that stays locked. The review of BUI-1224 and BUI-1228 asked for the new test in the locked script, and the loop needed a human.
- **REQ-GATE-43** When a workflow file (`.github/workflows/*.yml|yaml`) existing at base changes and the card names it (its `paths` match it, or its text names the path or the file name), the gate shall not lock it if a structural comparison shows it only appends plain run steps: top-level keys other than `jobs` are unchanged; the same job ids; every job keeps every key (`needs`, `if`, `name`, `runs-on`, `env`, `with`, `strategy`, `permissions`, …) unchanged; its `steps` keep every base step unchanged and in order; and each new step comes after them, has `run`, only `name`, `run`, `shell`, `working-directory`, or `timeout-minutes`, and no `${{ }}` expression; and a `run` that is a scalar (not empty, a list, or a map); and the job it joins already runs a configured command (the test command, a check, the files or held-out command) in a base run step, as a command: a line of the run text (a folded `>` block is one line) is the command or starts with it and a space, so `echo 'npm test is disabled'` or a `# npm test` comment does not count, while neither that job (outside `if`) nor the workflow `env` or `defaults` holds a `${{ }}` expression (a secret or the token in any spelling could reach a later step through env, `GITHUB_ENV`, or a checkout's git config), sets an `environment`, or grants a `write` or `id-token` permission. `src/workflow.js` parses a YAML subset with no dependency (block maps and lists, plain, quoted, and block scalars, one-line flow lists and maps, comments) and keeps how each value was written, so a quoting change counts as a change; a mapping key is stored as YAML reads it (`"env"`, `'env'`, and `env` are one key; a quoted and a plain spelling of one key are a duplicate), so a quoted `environment`, `permissions`, `env`, or `defaults` key cannot hide from the checks. Anything else (anchors, aliases, tags, multi-line plain, quoted, or flow values, tabs, several documents, duplicate keys) fails closed. A workflow the card does not name, a new or deleted one, a new job, and every change to a base job or step stay locked with a `why` that the corrective turn (REQ-RUN-32) shows. Changes to `runs-on`, `env`, or `with` values stay locked, since no structural rule shows they keep a check. Rationale: 8 of 46 human stops were locks on `quality.yml` that the issue itself said to change (BUI-1217, 1225, 1230). A step before a base step could change what it checks. A new job could report a required check name (from this file, another workflow, or another app). An added step with an action, `env`, `with`, or an expression could read secrets or the token or gain privileges; a plain run step in a job that already runs the test suite, with no secret, token, environment, or write permission in reach, runs candidate code with nothing the suite's own run lacks.
- **REQ-GATE-44** When a bug or feature card modifies an existing test file (REQ-GATE-4) and `approveAllowEdits` and `testFilesCommand` are set, the gate shall not lock the file in the static stage if the head file keeps every test name of the base file (JS/TS `it`/`test`, Ruby `it … do`, Python `def test_*`, Go `func Test*`; Rust, JUnit, and xUnit attributes by count), has no fewer assertions (assert/expect/should/refute/verify calls, Python `assert`, Go `t.Error`/`t.Fatal`; commented-out ones, and test calls or assertions written as text inside a string literal, do not count), and no more skip markers (REQ-GATE-6), and the base file has at least one test. Then two stages must pass: `test-edit-proof` (after the red proof) runs `testFilesCommand` for each such file alone, which must pass on head and, with only that file overlaid on base (the other edited files as on base, so one edit cannot make another file fail), fail with a real test failure; and `test-edits` (before the review) asks the reviewer, then only fallbacks of the reviewer's own family, to answer `APPROVE: <why the edited tests check at least as much>` or `DENY: <what the edit weakens>` given the card and the test diff, in a scratch checkout of head. Its result records `approval: { approved, by, reason }`, `reviewer` (the tier that answered, else the first asked), cost, and usage, which count as review spend (REQ-LED-13); when no regular review runs, that `reviewer` names the spend. An `allowEdits` path the other family approved in the run (REQ-RUN-30, the card's `approvedEdits`) is not exempt as a human `allowEdits` path is: it must keep every test name and skip count and have no fewer assertions (a deleted, renamed, or type-changed file stays locked), and on a bug or feature card with `testFilesCommand` it also goes through `test-edit-proof` and `test-edits`. A deleted, renamed, or type-changed test file, a refactor/ui/infra/chore card, a dropped test or assertion, an added skip, no reviewer, no answer, or a denial keeps the lock (`existing-test-changed` with a `why`). It extends REQ-RUN-30: that approves a request before the edit; this proves the edit after it. Rationale: 8 of 46 human stops were existing-test locks the change truly needed (BUI-1111, 1122, 1152); the counts and the per-file red proof are deterministic, and the verdict is from another family than the builder.
- **REQ-GATE-45** The gate shall record each command stage's wall time as `ms` on its result: install, every check, `regression-on-head`, and acceptance (the first run's time; a flaky retry is not counted), and every stage that yields one result (red proof, held-out, mutation, test edits, review), measured after its gate slot is granted, so queue time is not counted. The receipt carries `timing`, and `keel gate` prints it after the stage lines as one line, e.g. `timing lint 4s · test 3m12s · red-proof 40s · review 2m40s · total 6m36s`. Rationale: on 2026-10-16 nobody had noticed that BuildProven's 3,023 tests ran on one core while another product repo's ran on three; the ledger had one median gate time per card and no time per check.
- **REQ-GATE-46** When the gate writes a receipt, it shall append `{ repo, card, head, pass, at, checks: { stage: ms } }` to `gate-times.jsonl` beside the receipts dir (`repo` is the real git common dir, so every worktree of a repository matches) and return `IMPROVE:` lines, which `keel gate` and `keel run` print: one for each stage over its absolute limit (2 min; 5 min for `review` and `test-edits`), or more than 1.5× and 30 s over its median of the last 20 passing gates of that repository once 3 have timed it. Each line names the stage, its time, the limit or median, and the likeliest fix for that stage (run tests in parallel, `testFilesCommand` for the red proof, cache installs, split the card for review, lint changed files). When `testFilesCommand` is set but the red proof was not targeted (REQ-GATE-33), the red-proof line names why instead: the suite output names no new file and no `node --test` glob matches it (listing `unseen`), or the files command failed on head. It warns and never fails the gate. Rationale: friction that is only measured is tolerated; a named fix after every gate makes the gate improve itself.
- **REQ-GATE-47** The gate shall measure the time its stages wait for a gate slot (REQ-GATE-29), from asking to being granted, and record it as `waitMs` on the receipt and in its `gate-times.jsonl` row (REQ-GATE-46). The timing line leads with it when it is a second or more (`timing wait 4m12s · lint 4s · …`) and counts it in the total. A wait over a minute adds an `IMPROVE:` line that names it and its cause: other gates or work outside keel held the CPU or memory. Rationale: on 2026-10-16 a gate waited behind 2 others and 7 queued behind one slot, and nothing showed how much of a slow gate was queueing rather than work.
- **REQ-GATE-48** When the gate prepares a fresh checkout without `install` (REQ-GATE-16) and a `shareDirs` entry is missing in the repo it runs from but present in that repo's main worktree (the parent of `git rev-parse --git-common-dir`), the gate shall link the main worktree's directory. `keel run` links its worker worktree the same way. Rationale: a linked worktree (`.claude/worktrees/agent-*`) has no `node_modules`, so the checkout got no dependencies and the gate failed late at `lint` with `eslint: command not found`; on 2026-10-17 two agents each lost a 30–60 min queued gate run to this (BUI-1374).
- **REQ-GATE-49** When `keel.json` sets no `install` and writes `shareDirs` itself, and an entry of it exists in neither the repo nor its main worktree, the gate shall fail before it asks for a gate slot (REQ-GATE-29), as stage `prepare` with rule `missing-shared-dir` and the message `missing <dir> in <repo>: install dependencies there or set "install" in keel.json`. Written `shareDirs` are the dirs the checks need; the default `shareDirs` are only linked when present and never fail, because Keel cannot tell from them what a project needs (a Python repo that ignores `.venv` may run a system pytest). Rationale: the checks fail anyway without the dependencies, only after a long wait for a slot (BUI-1374).
- **REQ-SLOT-1** Unless `KEEL_GATE_SLOTS` fixes it, the gate slot count (REQ-GATE-29) shall follow the machine's measured idle CPU and memory: the gates running plus one per 2 idle cores, at most half the CPUs. Idle is the share of CPU time idle across all cores over a 1-second sample (`os.cpus()` time deltas). Under 20 % idle, or when memory is short (macOS: `kern.memorystatus_vm_pressure_level` critical or `kern.memorystatus_level` under 15 %; Linux: `MemAvailable` under 15 % of `MemTotal`), no new slot opens: the count is the gates running, at least 1. A waiting gate recomputes it every poll; with no slot held, a gate always runs, so load from outside keel cannot stop every gate. Rationale: at a load average of 78 on 8 cores, 2 slotted gates ran beside about 10 unslotted test runs, and everything ran 3–5 times slower (BUI-1185), so the cap and the saturated-machine floor stay. The load average was the wrong signal: on macOS it counts waiting threads and lags by minutes, so on 2026-10-16 it read 30.6 with about 45 % of the CPU idle, and 7 gates queued behind one slot. `os.freemem()` is not used: on macOS it leaves out reclaimable memory and read 0.7 % on a healthy machine.
- **REQ-SLOT-2** `keel test [--repo <dir>]` shall run `testCommand` from `keel.json` at HEAD in the working tree, with the candidate environment (REQ-RUN-12) and its output on the terminal, while holding a gate slot (REQ-GATE-29, REQ-SLOT-1), and exit with its exit code (1 when a signal ended it). It takes no argument. Rationale: builders run the suite before `keel gate` and after each fix; through `keel test` those runs queue with the gates instead of loading the machine beside them (BUI-1185).
- **REQ-SLOT-3** A gate's tickets shall all carry the gate's start time, so each heavy stage after the first queues ahead of gates that started later, and the oldest started gate finishes first; order is still by start time, so no gate starves. Rationale: with a ticket per stage request, a started gate's red-proof stage queued behind every gate that arrived during its first stage, and one gate waited through the whole queue 2–4 times (2026-10-13).

Run (dynamic model/effort)

- **REQ-RUN-1** When `keel run <card>` starts, Keel shall create a branch `keel/<card-id>` and a worktree (path keyed by repo path hash and card ID) from the base ref.
- **REQ-RUN-2** Keel shall choose the start tier from policy rules: size `L`, kind `infra`, or a planned path matching `protected` raises the start tier to the rule's minimum; otherwise tier 0.
- **REQ-RUN-3** When an attempt fails, Keel shall start the next attempt one tier higher with only the trimmed failure added to the prompt.
- **REQ-RUN-4** When the attempt passes, Keel shall stop and report the branch; where `--pr` is set, it shall publish exactly the certified SHA to the branch (after checking the branch tip equals it) and open a PR against the base branch using argument arrays only (no shell). If changed files touch `protected`, size is `L`, or kind is `infra`, the PR shall be a draft marked for human review.
- **REQ-RUN-5** If `maxAttempts` attempts fail, then Keel shall stop with a non-zero exit and keep the worktree for inspection, until the cleanup removes it (REQ-CLEAN-3).
- **REQ-RUN-6** Keel shall classify a failed worker: `auth` stops the run; `quota` moves to the next tier of a different provider at or above the tier floor, or stops if none (a raised floor never lands on the provider that is out); `network` retries the same tier per REQ-RUN-11; any other failure escalates as in REQ-RUN-3. A limit or login failure counts only in the exact form the claude and codex CLIs print it (`API Error: 429`/`401`, a whole unindented line `Error: 429 Too Many Requests`, `last status: 429`, `hit your usage limit`, `5-hour limit reached`, `rate_limit_error`, `insufficient_quota`, `Not logged in · Please run /login`, `unexpected status 401 Unauthorized`): worker output also holds the model's and the tests' text, and a stack-trace line `app.js:401:12`, a test named "rate limit middleware", an assertion `expected status code 401`, or an app's own `Error: 401 Unauthorized` once stopped a run as `auth` or `quota` (BUI-1191).
- **REQ-RUN-11** A worker failure that names a connection error, a timeout, or an explicit 502/503/504-class provider status shall be classified `network`, not `error` — a stronger model fixes nothing about a dropped connection, so escalating tier on a transient network failure only inflates cost with no signal. Keel shall retry the same tier up to 2 times on a `network` failure before escalating like an ordinary error, so a genuinely broken connection still does not stall the run forever.
- **REQ-RUN-12** Keel shall start workers and the configured checks with secret-looking environment variables removed — any name containing `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, or `PASSWD` as a whole underscore-separated word (so `LINEAR_API_KEY` and `AWS_SECRET_ACCESS_KEY` go, `KEYBOARD` stays) — except names listed in `keel.json` `workerEnvAllow` (default none). They also get no GitHub credentials, which live in files: `GH_CONFIG_DIR` is an empty dir (so `gh` and git's `gh auth git-credential` helper find no login), `GIT_CONFIG_NOSYSTEM=1` (no keychain helper), no `SSH_AUTH_SOCK`, and `GIT_TERMINAL_PROMPT=0`; `workerEnvAllow` can keep `GH_CONFIG_DIR` or `SSH_AUTH_SOCK`. Keel's own `git` and `gh` calls keep the full environment. Rationale: a model process must not inherit the operator's API keys; the operator's shell holds them for `keel poll` itself (found 2026-09-29, when `LINEAR_API_KEY` was exported for every shell). Credentials: candidate code could post the required `keel/gate` status itself (BUI-1151). This raises the bar; it is not an OS sandbox.
- **REQ-RUN-13** The builder prompt shall tell the worker that, when the card is impossible as written, already satisfied by the current code, or a test or check is defective, it must not work around the problem but write the reason to a file `KEEL_BLOCKED` in the worktree root and stop. If that file exists after a worker call, Keel shall remove it (so it is never committed), record the attempt with `workerStatus: blocked`, skip the gate, try no further tier, keep the worktree, and stop with `stopped: blocked` and the reason. The reason is stored in the ledger row (`blockedReason`) and printed by `keel run`. Rationale: the only escalation otherwise is a stronger model, which cannot fix a defective card or test, and pressure to pass is what drives test-gaming (§13).
- **REQ-RUN-14** For kinds `bug`, `feature`, and `ui`, the builder prompt shall tell the worker to put new tests in a new test file and not edit any existing test file unless the card's `allowEdits` names it. Rationale: existing tests are locked (REQ-GATE-4); in the 2026-10-03 pilot both QA-159 and QA-161 spent their first attempt on a locked edit to an existing test file, and plain Claude Code made the same edit.
- **REQ-RUN-15** The builder prompt shall ask the worker to run only the checks that cover its change and shall name the full configured checks the gate runs afterwards, instead of asking it to run the full checks. Rationale: in pilot round 1 a one-line workflow change took the worker about 10 min, mostly re-running the full test suite the gate then ran again; plain Claude Code ran targeted checks in 1–3 min.
- **REQ-RUN-16** With `--pr`, the PR body shall show the gate evidence: one row per stage (flaky marked), the red-proof test files that failed on base and pass on head, the held-out stage without its path, the passing tier with provider, model, and effort, the attempt number, and the run's summed cost (`n/a` when any attempt is unpriced). Rationale: review starts from what the gate proved (finish list F2).
- **REQ-RUN-17** Where `keel.json` sets `heldOutAuthorTier` (a tier index; default per REQ-RUN-28) and a card needs held-out tests (REQ-GATE-10) but names none, `keel run` shall first run that tier on a temporary checkout of base with a prompt to write tests only, from the card text, that fail on the current code. It keeps the new test files only if the held-out command fails on base as a real test failure that names one of them, copies them to a per-card directory under Keel's state dir (each test file under a `heldout_` name when the renamed tests still fail on base, so the builder's own test for the card never takes the same path and trips the gate's no-overwrite rule), and builds with that as `heldOut`; otherwise it stops `held-out-author` before any build attempt. The ledger records the authoring as a `held-out-author` row: its cost counts toward the card, not as an attempt. Rationale: held-out tests cost the founder time, so M/L cards stalled; a different provider writing them reduces shared blind spots (finish list F4).
- **REQ-RUN-41** When held-out authoring (REQ-RUN-17) stops a run before any build attempt, `keel run` shall remove the card's worktree and branch it created for that run; a kept head (REQ-RUN-24) stays. Rationale: on 2026-10-16 a Codex quota error stopped the author for BUI-1297, and the empty worktree it left blocked the next run.
- **REQ-RUN-42** When the next `keel run` starts on the same card after such a stop, it shall start without a "worktree exists" error.
- **REQ-RUN-18** The builder prompt shall tell the worker not to commit; Keel commits the worktree after each worker call (REQ-RUN-7). Rationale: on 2026-10-06 the Codex tier finished BUI-1047 and BUI-1044 with green targeted checks, then stopped blocked because its `workspace-write` sandbox cannot write the git dir of a linked worktree, so the finished work was lost.
- **REQ-RUN-19** The failure text for the next attempt shall add one repair line per failed rule: restore a locked file from base (or block naming the `allowEdits` the card needs), remove a bypass or skip marker at its line, undo an out-of-scope change, write a test that fails on the old code, or strengthen tests against surviving mutants. Held-out failures stay withheld. Rationale: `existing-test-changed` is the most common gate failure in the receipts (26 stages by 2026-10-06), and on BUI-1047 and BUI-1044 the next tier repeated the same violation from the rule name alone.
- **REQ-RUN-20** `keel run` and `keel poll` with `--merge` (implies `--pr`) shall, after a pass, enable GitHub auto-merge with `gh pr merge <pr> --auto --squash --match-head-commit <certified head>` only when merge readiness holds (REQ-CLI-4) and a protected, `infra`, or L change also passed held-out tests. Otherwise the PR stays open (a draft when risky) and its body and the Linear comment give the reason. The result records `merge` as `auto`, `off`, or `failed`; a failed merge call exits 1; a poll outcome with auto-merge on is `autoMerge`. Rationale: §9 owner rule, auto-merge when tested and reviewed (K2).
- **REQ-RUN-21** Where `keel.json` `learnStart` is true (default), `keel run` shall raise the REQ-RUN-2 start tier one step at a time while this repo's ledger shows the cheap first try does not pay: with p the share of the last 20 runs that started at the tier and passed on attempt 1 (a first try stopped as `blocked`, `quota`, `network`, `auth`, or `harness-error` says nothing about the model and is left out), and L, H the mean priced attempt cost at the tier and one up, it moves up when L ≥ p × H. Fewer than 5 such runs, or no priced attempt at either tier, keeps the tier. A tier that 10 later runs started above by learning (their `ruleTier` at or below it) is tried first again (a probe), so its numbers stay current. The run logs the reason, and each ledger row records `ruleTier`, `tierLabel`, and `ruleLabel`. Ledger rows are matched to today's ladder by tier label (REQ-RUN-35), not by the index they were written with. Rationale: on 2026-10-10 the ledger showed tier 0 (Sonnet low) passing first in 17/61 runs at a mean $0.38 per attempt, against $0.32 for tier 1, so cheapest-first cost more and took longer (DESIGN §8 economics).
- **REQ-RUN-23** With `--pr`, after the push and before the PR opens, `keel run` shall post the commit status `keel/gate` (`success`, description `passed; review by <reviewer>` or `passed; review off in keel.json`) on the certified SHA with `gh api`, before it enables auto-merge. If the post fails, it shall not enable auto-merge; with `--merge`, whatever the merge policy, the merge state is `failed` with the reason, so the run exits 1. Rationale: GitHub keeps auto-merge on after a later push by a user with write access, and `--match-head-commit` is checked only when auto-merge is enabled. A branch that requires `keel/gate` refuses any head the gate did not pass (found by Codex review, 2026-10-12; BUI-1138). The status goes to the repo `gh` resolves for `{owner}/{repo}`; in a fork with an `upstream` remote, set `gh repo set-default` to the repo the PR targets, or the post fails and auto-merge stays off.
- **REQ-RUN-24** When a gate fails only because the reviewer is unavailable (every other stage passed), `keel run` shall keep the card's worktree and branch at that head, mark the ledger row `pendingReview`, and return `pendingReview: true` with the stop `review-unavailable`. Rationale: on 2026-10-12 two builds that passed every other stage were thrown away when Codex hit its usage limit, and the next poll would pay to build them again (BUI-1143).
- **REQ-RUN-25** When a run starts and the card's last ledger row in this repo is `pendingReview` with a head that is still the tip of the clean worktree: on the same base, its first attempt (ledger `resumed: true`) shall gate that head again with the full gate, review included, instead of building; a pass continues as any pass (PR, merge), and a failure feeds the next tier as usual. When the base, the card (a hash of the card as written, recorded on every attempt row), or the builder tier entry (its hash, recorded too; the reviewer tier may change) has changed since, or the worktree no longer has the branch checked out at that head, it shall remove the kept worktree and build again. A kept branch still at that head whose worktree is gone is deleted and built again. A branch whose tip is no longer the kept head (moved ahead, back, or sideways) may hold work Keel did not make, so it is never deleted: the run stops with `worktree exists`, as for any other worktree. A clean kept worktree whose branch ref was deleted is removed and built again. Learned routing (REQ-RUN-21) ignores resumed attempts, in first tries and in priced samples, and a `pendingReview` first try is not counted as a failed one.
- **REQ-RUN-26** The builder prompt shall tell the worker not to do real work outside the card but to append one line per item to `KEEL_FOLLOWUP`: `<bug|feature|chore>: <title> — <why, with path:line>`. After each attempt, Keel shall read and remove the file (never committed, like `KEEL_BLOCKED`), keep at most 5 items per run with distinct titles (case-insensitive), cut each line to 300 characters, and return them as `followUps` (`{ kind, title, detail }`) on every stop after an attempt, an auth stop included. A line without a known kind is a `chore`. Rationale: owner goal 2026-10-12, under 5 % human interaction; found work was lost (BUI-1144).
- **REQ-RUN-27** On a pass, each non-blocking review note (REQ-GATE-21 `notes`) shall also become a follow-up: kind `bug`, title `Review: <text>`, detail `<severity> <path>:<line>`. Review notes have their own cap of 5, so builder items cannot crowd them out.
- **REQ-RUN-28** When `keel.json` does not name `heldOutAuthorTier`, Keel shall use the strongest tier whose family differs from tier 0's, or none when every tier is one family; an explicit `null` turns authoring off. Rationale: M/L cards in repos that did not set it waited for a human (BUI-1145); same pattern as review on by default.
- **REQ-RUN-29** When the worker process ran (exit status not null) and the only error is EPIPE, because it exited before reading its prompt, Keel shall classify the attempt from its exit code and output as for any other exit (REQ-RUN-6), not as `spawn-error`.
- **REQ-RUN-30** When a worker blocks the card (REQ-RUN-13) with `allowEdits: <path>` lines, every path is a test file (`testGlobs`) that exists at base, none is a verification file, and none is allowed yet, and `approveAllowEdits` is on (keel.json, default `true`): Keel shall ask the cross-family reviewer tier, then the fallbacks (REQ-GATE-22), to answer `APPROVE: <requirement>` or `DENY: <why>`, given the card, the paths, and the worker's reason, in a scratch checkout of the committed head (what the approver writes never reaches the build). On approval it shall add the paths to the card's `allowEdits` and `approvedEdits` (which the gate still proves, REQ-GATE-44) for the rest of the run, record `allowEditsApproved` on the ledger row, log it, and run the next attempt on the same tier with the approval as feedback; the result lists `approvedEdits`. On denial, or when no tier answers, the run stops blocked with the denial appended. Learned routing (REQ-RUN-21) does not count an approval attempt as a first try. The builder prompt tells the worker to write these lines. Rationale: a fix that changes behavior often must change the existing test that pins the old behavior (BUI-1152; SWE-bench django-14608); a human approved each one before. The approver is another family, and the gate, the review, and the PR still check the edited test.
- **REQ-RUN-31** Keel shall give a `claude` or `codex` worker its prompt on stdin (`codex exec -`), never as a command-line argument. Rationale: one argument has a size limit (cmux's `claude` wrapper rejects more than 122880 bytes; Linux allows 128 KiB), and a re-review prompt with the previous delta (REQ-GATE-23) went over it, so every Claude fallback failed at launch within seconds (BUI-1161).
- **REQ-RUN-32** After a worker call that ended `ok` and did not block, Keel shall commit the worktree (REQ-RUN-7) and run the gate's static stage alone on that HEAD. When `locked` or `scope` fails, Keel shall not escalate: it gives the same tier one corrective turn (continuing its session per REQ-RUN-33) that lists each offending path with its rule, says "revert your edits to these locked files; put new tests in new files" and to undo out-of-scope changes, and adds the REQ-RUN-19 repair lines, so an edit the card truly needs still goes to REQ-RUN-30 approval through `KEEL_BLOCKED`. The turn is part of the attempt: the ledger row sums both calls' usage and cost and records `corrective: { rules, paths }`. Then the attempt goes on as usual (blocked check, commit, full gate). One corrective turn per attempt. Rationale: on 2026-10-14, 35 % of all builder tokens went to attempts that failed `locked` (55 existing-test-changed, 21 verification-file-changed); tiers 1 and 2 failed the same way, and in 4 locked→locked retries the next tier left the head unchanged.
- **REQ-RUN-33** Keel shall record each worker call's CLI session (`session`: Claude's result `session_id`, Codex's `thread.started` `thread_id`, an exec worker's JSON `session_id`). When the next call runs on the same CLI (same provider; for `exec`, the same command), Keel shall continue that session (`claude -p --resume <id>`; `codex exec resume … <id> -` with `-c sandbox_mode="workspace-write"`; `KEEL_RESUME=<id>` for exec, never inherited from Keel's own environment) with a short prompt holding only the failure and the standing rules, and mark the row `continued`. Otherwise the fresh prompt shall list `git log --oneline <base>..HEAD` under "Your branch already has these commits". Rationale: each tier reused the worktree but started a fresh session that explored the repo again (about 0.5M cached tokens per attempt) without being told the earlier commits were there.
- **REQ-RUN-34** When the gate fails at a configured check or `regression-on-head`, the worker ended `ok`, and the worktree HEAD is still the gated head with no uncommitted change, `keel run` shall gate that same head once more before escalating, log it, and mark the row `regated`. A pass there passes the attempt, with the stage marked `flaky` in the written receipt, the PR body, and the row's `flaky` list (REQ-GATE-18); a second failure escalates as usual. Rationale: on 2026-10-14 four attempts failed test, lint, or build after REQ-GATE-18's in-gate retry, and the next tier then passed on the same head with no change, so each flake cost a whole attempt.
- **REQ-RUN-35** The default ladder shall be Sonnet 5.5 high, Opus 5.5 high, Codex gpt-5.6-sol high (§6.2), with start floors `L` 1 and `protected` 0, and learned routing (REQ-RUN-21) shall read ledger rows by tier label (provider, model, effort; for `exec`, also the command), so history written under another ladder is never counted for the tier now at its index. A row whose label is not on the ladder counts for no tier. A row without a usable label (no provider, or an exec row without `tierLabel`), and every row when two tiers share a label, keeps its index. A row without `ruleLabel` keeps how many tiers learning moved it (`tier` − `ruleTier`), counted from where its tier maps today. Rationale: on 2026-10-14 tier 0 (Sonnet low) cost $0.23 per attempt against $0.25 for Sonnet high but passed first in 30 % of first tries against 45 %; none of the 18 `keel.json` files sets `tiers`.
- **REQ-RUN-36** Where `keel.json` `fixLowFindings` is true (default; validated as a boolean), when an attempt of a `bug` or `feature` card passes the gate and its review lists notes (REQ-GATE-21 findings below `reviewBlock`, each naming a path and line, `info` included per REQ-GATE-41), and the card budget (REQ-RUN-22) is not spent, `keel run` shall give the same tier ONE corrective turn before accepting, continuing its session per REQ-RUN-33. With no session to continue (the attempt's last call printed none, or a kept head was gated without a call) there is no turn: a fresh session would explore the repo again, which costs more than the turn is worth. The turn lists each note as `- <severity> <path>:<line> <text>` and says: "Fix each one that is real, with a test where it is a behaviour; for one that is not real, reply why in KEEL_DISMISS lines (`KEEL_DISMISS <path>:<line> <reason>`) and change nothing for it." Keel then commits the worktree (REQ-RUN-7), reads `KEEL_FOLLOWUP` (REQ-RUN-26), and gates the new head; the attempt is accepted on that receipt when it passes. A turn that leaves HEAD unchanged and the worktree clean is not gated again: the earlier receipt stands. Notes in the accepted receipt still become follow-ups (REQ-RUN-27). Other card kinds, and a turn already taken this attempt, are unchanged. Rationale: an escape analysis of 48 Keel merges (2026-10-14) found all 3 real escapes flagged by the reviewer below the blocking level (BUI-1159 and BUI-1157 at low); as follow-ups they merged with the defect in them (BUI-1256).
- **REQ-RUN-37** When the REQ-RUN-36 turn breaks the gate, ends other than `ok`, blocks (`KEEL_BLOCKED` is read and removed), or leaves the branch, Keel shall never lose the passing result: it resets its own run worktree to the earlier passing head (`git reset --hard` and `git clean -fd` there only; it is Keel's worktree, never the user's checkout) and accepts the attempt on the earlier receipt, logging why. An error thrown during the turn (worker, commit, or re-gate) is handled the same way and recorded as the row's `error`. When that restore itself fails (for example a stale `index.lock`), the worktree cannot be accepted: the run throws the error after the row is recorded with `outcome: "restore-failed"`.
- **REQ-RUN-38** Each REQ-RUN-36 turn shall append its own ledger row with `role: "fix-findings"`, the attempt and tier, the turn's `usage`, `cost`, `durationMs`, `continued`, the re-gate's `gateMs` and `reviewCost`, the `notes` count, `dismissed` (`{ path, line, reason }` parsed from the worker's `KEEL_DISMISS` lines), `outcome` (`fixed`, `unchanged`, `reverted`, or `restore-failed`), and the accepted `head`. Card budget (REQ-RUN-22) counts it; learned routing (REQ-RUN-21) and the attempt count of `keel report` do not. `keel report --escaped` (REQ-LED-6) counts a run at its last passing row, so a fixed turn's head replaces the attempt's. `keel report` shall print `findings turns: <n> (fixed <a>, unchanged <b>, reverted <c>[, restore failed <d>]); cost <$x>` when any exist, so their cost is visible.
- **REQ-RUN-39** Where `keel.json` sets an integer `heldOutAuthorTier` at or past the length of the default tiers but below 4 (the default ladder's length before REQ-RUN-35), and does not set `tiers` itself, Keel shall use the REQ-RUN-28 default (the strongest tier of the other family) and print `keel: WARN keel.json heldOutAuthorTier <n> is past the default tiers (<len>); …` on every load; past tiers that `keel.json` sets, it stays a config error. Rationale: REQ-RUN-35 cut the default ladder from four tiers to three, and nine repos' `heldOutAuthorTier: 3` (the Codex tier then) stopped every `run`, `poll`, and `gate` there, including the gates of the PRs that would remove it, since policy is read from base (BUI-1258).
- **REQ-RUN-40** When a Keel process that built a candidate environment (REQ-RUN-12) exits normally, it shall have removed every empty `GH_CONFIG_DIR` dir (`keel-nogh-*`) it made, including one it replaced because candidate code wrote into it. A replaced dir is kept until exit, since a candidate process started with it may still run. A `GH_CONFIG_DIR` in `workerEnvAllow` makes no dir and is never touched. Rationale: each process, and each dir candidate code dirtied, left one `keel-nogh-*` dir in the temp dir, so a machine running `keel poll` or many gates filled it (found with BUI-1214).
- **REQ-RUN-22** Where `keel.json` sets `cardBudgetUsd` (a positive number; default none), `keel run` shall stop with `budget` after a failed attempt once the run's priced cost (attempts, held-out authoring, review) reaches it, keeping the worktree. Unpriced attempts cannot count and are not treated as zero cost.
- **REQ-RUN-7** After each worker call, Keel shall fail the attempt if the worker left the `keel/<id>` branch, else commit any uncommitted changes (argv only) so the gate sees them. A worker that left the branch fails only its own attempt: Keel puts the worktree back on `keel/<id>` (forced checkout, untracked files removed) before the next attempt; once, every later tier failed on the same detached HEAD.
- **REQ-RUN-8** Keel shall append the per-provider `workerArgs` from config to each worker command, and give `exec` workers `workerArgs.exec` and the tier's model and effort as `KEEL_MODEL` / `KEEL_EFFORT`.
- **REQ-RUN-9** An attempt shall pass only if the worker finished successfully and the gate passed. The ledger stores this as `attemptPass`, and the report uses the same rule.
- **REQ-RUN-10** `keel run` shall hold an exclusive lock for (repo, card) for its whole duration. A second `run` on the same card while the lock is held by a live process shall fail immediately with a distinct, attributable error, never race the first run's `git worktree add` or silently produce two worktrees for one card. A lock left by a process that is no longer running shall be reclaimed automatically, since that is an ordinary crash-recovery case, not a live conflict. Each run writes its own lock entry named by its pid (and a counter, so two runs of one process differ) and then lists the card's entries, holding the lock only when no other entry belongs to a live process; whoever lists second sees the other's entry, so two runs never both hold a card (two that start at the same moment can both yield). An entry of a dead process, or one naming no process id, is a crash leftover that any run removes; no live entry is ever moved or deleted by another process. Runs of an older Keel and a newer one never overlap, in either order: a live `<lock>/pid` of the earlier layout also holds the card, and the holder keeps `<lock>/pid` with its own pid (renamed into place, so never without one; a dead run's is replaced) until it releases, so an older run's `mkdir` of `<lock>` fails and it reads a live pid. Earlier designs (a pid file written after the lock dir; a stale lock moved aside and back) left a lock without an owner or let a third run slip in during a reclaim.

CLI

- **REQ-CLI-1** `keel --help`, `keel -h`, and `keel` with no command shall print the usage text to stdout and exit 0.
- **REQ-CLI-2** If an option is unknown, a command is unknown, a required argument is missing, `--repo` is not a directory, or `keel init` finds no project marker or no test command, then Keel shall print one `keel: <reason>` line and the usage text to stderr and exit 2, never a stack trace. Only these usage errors are handled this way; every other error stays visible as thrown.
- **REQ-CLI-3** `keel doctor [--repo <dir>] [--base <ref>]` shall load the config at base, prepare a fresh checkout of base exactly as the gate does (REQ-GATE-16: `install`, else linked shared dirs), then run every check and the test command and print one `PASS`/`FAIL` line each. It shall also run each `acceptance` command and print it as `INFO` (`green` or `red`): a fix card's acceptance is expected to be red at base and never fails the doctor. It exits 0 only when every check and the test command pass at base, 1 otherwise. Rationale: a check that is red or unrunnable at base makes every card fail at every tier (found 2026-09-30).
- **REQ-CLI-4** Merge readiness: `review` is on, the repository allows auto-merge (`allow_auto_merge`; off prints `merge-ready no (auto-merge is off in the repository settings)`), and the base branch (`keel doctor`: `--base`, else origin's default branch, else the current branch) has at least one required status check (branch protection or a ruleset, read with `gh api`, the branch name URL-encoded; an error counts as none, so GitHub cannot merge before CI). `keel doctor` prints `INFO merge-ready yes|no (<reason>)`, then `INFO keel/gate required yes|no (…)`: whether the base branch requires the `keel/gate` status (REQ-RUN-23); a `gh` error counts as no. Readiness does not need it, since a Dependabot or human PR cannot post it; without it the auto-merge gap of REQ-RUN-23 stays open. Rationale: K8.
- **REQ-MERGE-1** Self-merge fallback: with `--merge`, when merge readiness (REQ-CLI-4) fails only because GitHub auto-merge is unavailable (no required status checks on the base branch, or `allow_auto_merge` off), or the `gh pr merge --auto` call fails on an open PR, and the rest of the merge policy holds (review on, held-out tests for a protected, `infra`, or L change, `keel/gate` posted, REQ-RUN-20, -23), `keel run` shall keep the merge state (`off` or `failed`) with its reason, add `selfMerge: true`, open the PR as ready (not a draft), and end the body's `Auto-merge: off — <reason>` line with `; keel poll --merge merges this certified SHA itself once every check on it passes`. It merges nothing itself. `keel poll --merge` shall then record a `self-merge` row (PR URL, certified SHA, time) in the poll ledger, before any Linear call, comment `GitHub auto-merge is unavailable (<reason>), so keel poll --merge merges <sha> itself once every check on it passes`, and move the issue to review; the outcome is `selfMerge`. Rationale: GitHub refuses branch protection and auto-merge on a private repo of a free account (HTTP 403), so every passing Keel PR in a private product repo waited for a human (BUI-1271).
- **REQ-MERGE-2** At the start of each `keel poll --merge` (never without `--merge`), for each `self-merge` row of the repo that no later `self-merged`, `self-merge-failed`, or `self-merge-closed` row for the same PR settles, Keel shall read the PR (`gh pr view --json state,isDraft,headRefOid,mergeable,mergeStateStatus,statusCheckRollup`) and the workflow runs on the certified SHA (`gh api repos/{owner}/{repo}/actions/runs?head_sha=<sha>`), and merge with `gh pr merge <pr> --squash --match-head-commit <sha>` only when the PR is open, not a draft, its head is the certified SHA, every check run is completed with `SUCCESS`, `NEUTRAL`, or `SKIPPED`, every commit status is `SUCCESS` and `keel/gate` is among them, every workflow run is completed with `success`, `neutral`, or `skipped`, and the merge state is `CLEAN` or `HAS_HOOKS`. A merge records `self-merged`, logs `<ID>: merged <pr> at <sha>`, and gives the poll result `merged`. Anything not yet known (a check not completed, `keel/gate` absent, a queued workflow run, merge state `UNKNOWN`, `BLOCKED`, or `UNSTABLE`, a `gh` read error) leaves the row pending and logs `<ID>: self-merge waits for <names>`; the poll goes on, and a later poll checks again, so no poll waits on CI. Self-merge rows are not attempts of the issue (REQ-LINEAR-6): a deferred issue stays retryable.
- **REQ-MERGE-3** A pending self-merge shall not merge, and shall be reported, when its PR head is not the certified SHA (`head <x> is not the certified <sha>`: a human pushed after the gate), a check, status, or workflow run failed (`check <names> failed`), the branch is behind its base (Keel never changes the certified head), the PR is a draft, or `gh pr merge` fails. Keel records `self-merge-failed` with the reason first, then comments `keel: not merged: <reason>. The PR stays open for a human.` on the PR (`gh pr comment`; a failure is logged) and on the issue, logs it, and gives the poll result `mergeFailed`, so the poll exits 1. The PR stays open. A PR that GitHub reports `CONFLICTING` is left to REQ-LINEAR-23; a PR merged or closed outside Keel records `self-merged` or `self-merge-closed` without a comment.
- **REQ-MERGE-4** `keel.json` may set `selfMergeTimeoutMinutes` (a positive number, default 30). A self-merge still waiting (REQ-MERGE-2) when a poll finds it more than that many minutes after its `self-merge` row shall fail as in REQ-MERGE-3 with `checks not green after <n> minutes: <names>`: a workflow that never reports is a timeout, not a pass.
- **REQ-MERGE-5** When the `gh pr merge --auto` call fails on an open PR (REQ-MERGE-1), `keel run` shall rewrite the PR body with `gh pr edit <pr> --body`, so its `Auto-merge: on` line becomes `Auto-merge: off — <reason>; keel poll --merge merges this certified SHA itself once every check on it passes`; a failed edit is logged. Rationale: the body is written before GitHub answers the auto-merge call, so a refused call left a body that said auto-merge was on (BUI-1351).
- **REQ-MERGE-6** A pending self-merge whose merge state is `BEHIND` shall fail as in REQ-MERGE-3 (`the branch is behind its base`) at once, whether or not its checks are still pending: Keel never moves the certified head, so waiting cannot make it mergeable. A failed check is still reported first. Rationale: a pending check made the poll wait until the timeout and report a wrong reason (BUI-1350).
- **REQ-MERGE-7** Keel shall read every page of the workflow runs on the certified SHA (`gh api --paginate repos/{owner}/{repo}/actions/runs?head_sha=<sha>&per_page=100`, one JSON array a page), so a workflow run past the first page that is pending or failed blocks the merge as in REQ-MERGE-2 and -3. Rationale: the API returns 30 runs a page by default, and runs past the first page were ignored (BUI-1349).

- **REQ-CLI-5** `keel --version` and `keel -v` shall print the installed package version and exit 0.
- **REQ-CLI-6** `keel gate` without `--base` shall use origin's default branch: `refs/remotes/origin/HEAD` when it names an existing commit, else `origin/main`, else `origin/master`, and print `keel: base <ref>`. With none of them it is a usage error (REQ-CLI-2). Rationale: the gate before a PR is one command (`keel gate`), replacing the retired `/bs:quality`.
- **REQ-CLI-7** `keel gate` without `--card` shall gate with a card derived from the branch and print one line naming it: the ID is the branch name with every run of characters outside `[A-Za-z0-9._-]` replaced by `-` (max 64; a detached HEAD uses the short commit ID); size `S`; no paths, allowEdits, acceptance, or held-out tests; the kind comes from the conventional-commit types of the commits base..HEAD (`type`, `type(scope)`, and `!` forms): `feat` → feature, then `fix` → bug, then `ci`/`build` → infra, then `refactor`/`perf` → refactor, any other type → chore, the first of these that any commit has. No commit with a conventional type is a usage error that asks for `--card`. Rationale: a person's own branch needs no card file; red proof still applies to feature and bug, and scope, size, or held-out tests still need a real card.
- **REQ-CLI-8** `keel run <ID>`, where the ID matches `[A-Z]+-[0-9]+` and no file of that name exists, shall build that Linear issue exactly as `keel poll --issue <ID>` with the same options and exit codes. A file of that name is read as a card.
- **REQ-CLI-10** `keel gate --status` shall post `keel/gate` on HEAD after the gate: `success` as in REQ-RUN-23, `error` with `review unavailable (<status>); gate again later` when the only failure is an unavailable reviewer (the change was not judged), or `failure` with `failed at <stage>`, plus `: <first rule>` when the stage names one (a failed `keel.json` check names none). It prints `keel: status keel/gate <state> on <sha>`. If the post fails (for example, the commit is not pushed), it prints `keel: status keel/gate not posted: <gh output>` and exits 1. `--status` on another command is a usage error. Without `--status`, nothing is posted. This is how a PR made outside `keel run` meets a branch that requires `keel/gate`.
- **REQ-CLI-11** `keel audit [--limit N]` shall read the merged PRs that REQ-CLI-12 selects with `gh`, and for each whose `keel/gate` description names a fallback reviewer (REQ-GATE-22) and that `audit.jsonl` in the state dir does not list, review the merge commit against its first parent with the reviewer that was out (the tier whose `provider/model/effort` the description names), with no fallback. Blocking findings and notes join the found-work queue (REQ-LINEAR-22) as `bug` items titled `Audit #<PR>: <text>`, under the issue the PR body closes (`Closes <ID>`), or with no source when the body closes none, so the next `keel poll` files them; a finding is never dropped for a missing `Closes` ID (on 2026-10-13, five findings, one high, had been). Each audited merge is appended to `audit.jsonl` and never reviewed again. When the reviewer is still unavailable, it records nothing and stops; the next audit retries. It prints one line per merge and exits 1 on findings, 3 when the reviewer is out, else 0. Rationale: a fallback review can share the builder's family, so it is weaker; the cross-family review still happens, just later (BUI-1150).
- **REQ-CLI-12** `keel audit` shall read every PR merged in the last 30 days, up to `--limit` (default 500), not a fixed count of the newest: on 2026-10-14 keel merged 29 fallback-reviewed PRs in a day, and the newest-20 window left 9 never audited (BUI-1251). A merge `audit.jsonl` lists for the same repository (its real git common dir, so every checkout, linked worktree, and symlink of it matches; a commit can be in two repositories) is skipped without an API call, a gate status is read from a page of 100 statuses (GitHub returns 30 by default), and a merge whose `keel/gate` names no fallback is appended there as scanned, so no later audit fetches its statuses again.
- **REQ-CLI-13** `keel doctor` shall print each command's time (`PASS check lint (4s)`), and after the checks print `WARN` speed advice that never fails it: when the test command took over 60 s and runs on one worker (pytest without `-n`/`--numprocesses` in the command or in `addopts` of `pytest.ini`, `pyproject.toml`, `setup.cfg`, or `tox.ini`; `node --test --test-concurrency=1`; `jest --runInBand`/`-i`; `vitest --no-file-parallelism`), naming the fix; and when two checks (the test command included) run the same command, after expanding `npm test`/`npm run <script>` through `package.json` scripts and splitting on `&&`, `||`, and `;`. Rationale: as REQ-GATE-45; a serial suite and work run twice are the commonest gate waste, and the doctor has just measured both.
- **REQ-CLI-14** `keel doctor` shall judge a slow test suite by its measured time, not by the command's shape: when the test command took over 60 s and REQ-CLI-13 finds no serial runner (a wrapper script, or a suite that is already parallel), it prints `WARN tests took <time>; find the slowest tests (pytest --durations=30, …) and fix their cause: sleeps, real subprocesses or network, fixtures rebuilt per test`. The gate's IMPROVE lines (REQ-GATE-46) already judge every stage by measured time. Rationale: on 2026-10-16 a product repo's suite took 13m05s on 3 workers behind `python3 tools/run-quality-gate.py test`, and the doctor said nothing.
- **REQ-CLI-9** `keel gate` (no builder) shall review with the strongest tier whose family differs from the author's: `--author <family>`, else `KEEL_AUTHOR`, else `claude` when `CLAUDECODE=1` (set by Claude Code); with no known author, the strongest tier. A known author with no tier of another family fails `no-cross-reviewer`. With review on, it prints `keel: reviewer <provider>/<model> (author <family|unknown>)`. `--author` on another command is a usage error. Rationale: a Codex session that gated its own work was reviewed by Codex (found 2026-10-12).

Ledger

- **REQ-LED-1** Keel shall append one JSON line per attempt, even when the gate throws: card, attempt, tier, provider, model, effort, tokens (`in` = uncached input, `cacheWrite` = Claude cache writes, `out`, `cached` = cache reads, normalized across providers), estimated cost, worker and gate time, worker status, gate pass, head SHA. Every JSONL state file (ledger, poll ledger, audit, review spend) is read and appended one way. An append is one whole line in one O_APPEND write, never a truncate or rewrite, because several pollers and gates append at once and a rewrite could delete a row still being written. A line that does not parse (a write in progress or a crash leftover) never stops a reader: a whole row appended onto a cut-off fragment is recovered from the line's end; otherwise the line is skipped with a warning naming the file and line. Losing a row is worse than skipping a corrupt one; once, one cut-off line made every run, poll and report throw.
- **REQ-LED-2** If the worker output has no usage data, then Keel shall record `usage: null` and `usageMissing: true`.
- **REQ-LED-3** `keel report` shall print per run: attempts, passing tier, tokens, cached tokens, time, and the share of all runs (failed included) whose passing attempt (`attemptPass`) was on tier 0.
- **REQ-LED-4** `keel report` shall also print, per run, the summed estimated cost (`n/a` when any attempt of that run has no cost data), and a footer with accepted cards, tokens per accepted card, and cost per accepted card. Failed runs' spend counts toward the totals. When any attempt is unpriced the footer shall say so and show the priced total as a lower bound; with no accepted card it shall show `n/a`.
- **REQ-LED-5** `keel report` shall also print the median wall time (worker plus gate) per accepted card and the median gate time per attempt, `n/a` when there is no data. These are the G1 measures.
- **REQ-LED-6** Each `keel run` ledger row shall record its base commit. `keel report --escaped` shall, for each accepted run, find its merge on the repo's default branch (`origin/HEAD`, else `HEAD`) by patch identity of base..head or, for a Linear-style card ID, by the ID in the subject, and list each later `fix:` commit within 30 days of the merge that changes lines the merge wrote (REQ-LED-10), and each revert that names the merge, and print how many merges were "later fixed on the same lines or reverted". A merge commit counts once, for the earliest accepted run that landed in it (two runs of a card, as when a conflicting PR is rebuilt, REQ-LINEAR-23, once counted twice in `--escaped` and `--dora`). A run without a base (older rows use the gate receipt), a missing repo, or no merge found is listed with the reason, never dropped. Rationale: judging value needs escaped defects (finish list F1).
- **REQ-LED-8** `keel report --value` shall print, for the repos with merged Keel changes (REQ-LED-6), the share of Keel merges "later fixed on the same lines or reverted" and the same share, by the same rule (REQ-LED-6, REQ-LED-10), for every other non-merge commit on those default branches from a day before the oldest accepted run; and accepted runs of all runs with the cost per accepted card (REQ-LED-4). It decides nothing. Rationale: the former value test (0 escaped defects, ≥ 10 cards, ≤ $1.50, by a fixed date) had no baseline, so one heuristic `fix:` hit would have "failed" Keel even when hand-written changes fail more often.
- **REQ-LED-10** A later `fix:` commit shall count against an earlier change (`--escaped`, `--value` for Keel merges and the baseline alike, `--dora`) only when it modifies or deletes lines that change wrote, by `git blame` at the fix's parent; a pure insertion counts against the lines on either side of it, since it lands inside their code. Doc and requirements files (`*.md`, `*.txt`, `*.rst`) and lockfiles are left out: a prose edit or a dependency bump is not a defect. A revert that names the change always counts. Rationale: on 2026-10-14 the file-level rule said 22 of 48 Keel merges (46 %) were later fixed against a 64 % baseline, because every keel fix edits `docs/DESIGN.md`; hand review found 3 real escapes. By lines the shares were 21 % and 33 %.
- **REQ-LED-11** The lines each fix commit changes, with the commits that wrote them (REQ-LED-10), shall be cached in `<stateDir>/blame/<repo hash>/<sha>.json` and read from there on later reports. A commit never changes, so the answer never goes stale. Blame follows renames, and SHA-256 repositories work as SHA-1 ones do. A cache that cannot be written is reported once on stderr, and the report still answers. Rationale: the baseline asks the same fixes about every earlier commit, and one `git blame` per fix file is the slow part.
- **REQ-LED-9** `keel report --value` shall also print, per repo in the ledger, the summed routed cost of its attempts and the cost the same token usage (input, cache writes, cache reads, and output) would have had at the top (last) tier, priced from that tier's `priceInPerM`, `priceCachedPerM`, and `priceOutPerM` in `keel.json`, labelled "estimate". Cache reads are priced because the routed cost includes them, and cache writes at 1.25 times `priceInPerM`, Anthropic's 5-minute cache-write rate; without them an all-top-tier history would estimate below its own routed cost. A missing price that the tokens need or an unreadable `keel.json` prints `n/a` with the reason, never zero; an attempt with no usage or cost makes its figure a lower bound (`≥`). Rationale: routers prove value against a fixed model; Keel's "cheapest model that passes" claim needs a number.
- **REQ-LED-7** `keel report --dora` shall print, per repo with accepted runs, for Keel changes merged in the last 30 days: merges per week, median lead time (first attempt start to merge), change failure rate (merges with an escaped-defect candidate or a revert, REQ-LED-6, ÷ merges), and median time to restore (merge to the first such commit). A repo with no merge says so. Rationale: the Learn stage of §9 (K7).
- **REQ-LED-12** When a worker CLI reports usage but no cost (Codex prints none), Keel shall price the attempt from its tier's `priceInPerM`, `priceCachedPerM`, and `priceOutPerM` (cache writes at 1.25 × `priceInPerM`, REQ-LED-9), for builders, reviewers, and allowEdits approvers alike; a tier without a price that the usage needs leaves the cost `null`, never zero. The default tiers carry list prices (§6.2, source and date in `src/config.js`). The report prices an older row that has usage but no cost by its provider and model from the default tiers, and a review by the reviewer its row names. An attempt with no usage (a Claude timeout that printed no result) stays unpriced, and `--value` says how many. Rationale: on 2026-10-14 every Codex attempt and every Codex review in the ledger was unpriced, so the cost per card left out a whole provider.
- **REQ-LED-13** Each attempt row shall record `reviewUsage`: the usage of the review (every reviewer that ran, REQ-GATE-22) or of the allowEdits approval (REQ-RUN-30) of that attempt. For an older row without it, the report reads the review usage from the gate receipts of that card and head written during the attempt's gate time (`<card>-<head>-<ms>.json`). The per-finished-card figures of `--value` shall show builder and review separately and their total, for tokens and for cost; a review with no usage or no price counts as unpriced; when only some reviewers of a chain had a price, the row keeps the priced part in `reviewCost` (it still counts toward `cardBudgetUsd`) and sets `reviewUnpriced`, so the report shows a lower bound. Reviews outside a run (a `keel gate` by hand, `keel audit`) are not a card's cost. Rationale: on 2026-10-14 reviews had used 12.3 M tokens over 253 reviews, more than the builders, and tokens per accepted card left them out.
- **REQ-LED-14** `keel report --value` shall print the human touch rate, the G3 measure (§2): of the issues `keel poll` ran (poll-ledger rows with a run outcome; an issue that was only `deferred` is not decided yet and is left out), the share a human had to touch. An issue is untouched only when all of these hold: (a) none of its poll outcomes is a stop or a hand-over to a human (`blocked`, `failed`, `needsReview`, `inReview`, `closed`, `prFailed`, `reportFailed`, `closedMeanwhile`), and none is an explicit `--issue` retry; (b) Keel itself enabled the merge (`autoMerge`), so no human merged it; (c) a PR from `keel/<ID>` merged with a head SHA that the gate certified for that card (a ledger row with `attemptPass` and that `head`), so nobody pushed a commit after Keel; (d) no GitHub `User` (any author whose GraphQL `__typename` is not `Bot`) reviewed or commented on that PR; Keel itself writes none. An `autoMerge` issue whose PR is still open is pending and left out; one with no merged and no open PR is touched. Commit author emails are not used: Keel's workers and the owner's interactive agents commit under the same machine identity (`OSS Sync Bot`), and a squash merge credits the PR author, so neither tells a human from Keel; the certified head does. It prints `Human touch rate: X% (n of m issues; target under 5%)`, the touched issues by reason, and the runs that stopped for a human: the run's last attempt `blocked` (`KEEL_BLOCKED`) or `auth`, and poll `needsReview` decisions. A repo where `gh` fails prints the reason, and its undecided issues are counted as unknown, never as untouched. Rationale: G3 set the target (owner, 2026-10-12) with no measure.
- **REQ-LED-15** `keel report --value` shall lead with short plain-language lines a non-engineer can read: `Finished cards: X of Y (Z%)` (a finished card is an accepted run, REQ-LED-4), the human touch rate (REQ-LED-14), `Tokens per finished card: builder A + review B = C` (k and M units), `Cost per finished card: builder $A + review $B = $C` (with `≥` and the unpriced count when any is unpriced), and `Later fixed on the same lines: Keel X% (a of b) vs other work Y% (c of d)` (REQ-LED-8). The per-repo routed-cost lines (REQ-LED-9) follow under `Cost by repo`. Rationale: the owner reads it to judge Keel; engineer wording hid what each number meant.
- **REQ-LED-16** The human touch rate (REQ-LED-14) shall count, by default, only issues whose latest poll row is within the last 30 days (`value` window), and print `  Window: last 30 days (since YYYY-MM-DD)`. An `--issue` run (a poll row with `byHand: true`, REQ-LINEAR-14, or, written before 2026-10-17, the detail `explicit --issue retry`) that is the issue's first run (no earlier run row other than `deferred`) is a human start, not a touch: it is reported as `  Started by hand: N issues (M merged with no other human step)`; an `--issue` run after an earlier run is `retried by hand`. Stops for a human are counted by issue, among polled issues only (hand-written cards are not polled): an issue whose Keel runs (ledger rows of that card in that repo) ended `blocked` or `auth`, or whose poll outcome is `needsReview`, printed as `  Stops for a human: N issues (builder blocked a, login b, decision c)`. Legacy outcomes are left out: `closed` rows, and `inReview` rows before 2026-10-06, when `--merge` did not exist yet so every pass waited for a human merge. An issue with a `notKeel` outcome (REQ-LINEAR-25) is not Keel work: left out, and counted as `  Not keel work: N issues`. An `alreadyDone` issue (REQ-LINEAR-30) with no other human step is untouched. Self-merge rows (`self-merge`, `self-merged`, `self-merge-closed`, REQ-MERGE-2) are not runs; `self-merge-failed` (REQ-MERGE-3) is a stop for a human. Rationale: the rate read 79 % (66 of 84) on 2026-10-14, but 9 of the 16 `--issue` runs were first runs started by hand, `builder blocked 46` counted runs and 8 hand-written cards, and 5 issues predated `--merge`.

- **REQ-LED-17** Each refine turn (REQ-LINEAR-32) shall append a ledger row with `role: "refine"`, the issue as `card`, its own `run`, `attempt: 0`, the tier, `workerStatus`, `usage`, `cost`, `durationMs`, and `outcome` (`card`, `done`, `split`, `human`, `unparsed`). It counts toward `dailyBudgetUsd` like any priced row, is not a run in `keel report` nor an attempt for learned routing (REQ-RUN-21), and never hides a kept `pendingReview` head (REQ-RUN-25). `keel report` shall print `refine turns: N (card a, already done b, split c, needs human d, unparsed e); tokens T; cost $X` (`≥` when any is unpriced) when any ran.
- **REQ-LED-18** `keel report` shall end with the slowest check per repository: for each repository in `gate-times.jsonl`, the stage with the highest median over its last 20 passing gates, as `  <repo>: <check> <median> (<n> of <gates> gates)`, slowest repository first, or `slowest check per repo: no timed gates yet`. Rationale: one place to see where gate time goes across every repository (REQ-GATE-46).

Projects (any language, build system, or project type)

- **REQ-PROJ-1** The gate shall depend only on git, file globs, and the commands in `keel.json`; it shall assume no language runtime, package manager, or build tool.
- **REQ-PROJ-2** `keel init` shall detect the project from marker files and write a proposed `keel.json` (never overwriting one): Node (npm/pnpm/yarn/bun by lockfile; `test`, `lint`, `typecheck`, `build` scripts when present, run as scripts: bun uses `bun run <name>`, because `bun test` and `bun build` are its own test runner and bundler), Python (uv / poetry / pip; pytest; ruff and mypy when configured), Go, Rust, Ruby, Make (`test` target), and Terraform. Several markers at the root combine their checks (monorepo), except a Makefile with a `test:` target always supplies both `checks.test` and `testCommand` together — it is the project's own declared entry point, and a raw language detector's direct invocation must never silently disagree with what `make test` actually runs (real bug found and fixed 2026-09-28, on a real repo, the day after this requirement was first written). With no marker it shall fail and list the keys to set.
- **REQ-PROJ-6** Where `.github/workflows/` holds a YAML file, `keel init` shall propose the check `actionlint -shellcheck= -pyflakes=` first in `checks`, and shall not change `testCommand`. Rationale: the 2026-10-03 pilot found a workflow that passed every check but used a function GitHub rejects at run time, and the same invalid `actions/stale` input in four repos; actionlint reports both.
- **REQ-PROJ-7** `keel init` shall write `.github/workflows/keel-post-deploy.yml` into a Vercel project (`vercel.json` or `.vercel/`) unless that file exists. On a successful `Production` deployment it runs `keel.json` `smoke` (a command; default none, which warns that nothing was verified) with `KEEL_DEPLOY_URL`, three tries. On failure it marks the deployment failed and opens a revert PR with auto-merge (`KEEL_BOT_TOKEN` lets CI run on it); Vercel deploys the revert like any merge. Event fields reach the shell only through `env`. Rationale: with auto-merge, merge is production (§9, K3).
- **REQ-PROJ-8** The post-deploy workflow shall read `smoke` from the default branch with `persist-credentials: false`, never from the deployed commit; give write access only to a `respond` job that runs on a failed smoke test; revert exactly the deployed commit, only if it is on the default branch, under the subject `revert: <sha> failed the post-deploy smoke test`; mark that deployment's GitHub status `failure`; use one concurrency group per run; report a missing `KEEL_BOT_TOKEN` as an error; leave the run red; and never call `vercel rollback`, which turns off auto-assignment of production domains (later deploys would not go live) and needs a state machine to undo safely. Rationale: on 2026-10-07 the K1 review stage found injection, privilege, and rollback-state defects in earlier versions of this template; recovery by revert is slower (CI plus build) but has no hidden state.
- **REQ-PROJ-3** Default `testGlobs`, skip markers, and bypass markers shall cover JS/TS, Python, Go, Rust, Ruby, Java/Kotlin, C#, PHP, and shell; bypass markers include file-level and inline-config forms (`# ruff: noqa`, `# mypy: ignore-errors`, `# pylint: disable`, `/* eslint <rule>: "off" */`, `biome-ignore`, `prettier-ignore`), not only line comments (BUI-1203).
- **REQ-PROJ-4** Default `verificationPaths` shall include task/build runner files (Makefile, GNUmakefile, justfile, Taskfile, noxfile, tox, lint/type/test/format tool configs and their ignore files), and the package manager configs that change how scripts run (`.npmrc`, `.yarnrc*`): a new `.npmrc` with `script-shell=/usr/bin/true` once made every `npm` check exit 0 (BUI-1192). For `pyproject.toml`, only the test/lint/type tool sections (`[tool.pytest*]`, `[tool.coverage*]`, `[tool.ruff*]`, `[tool.mypy*]`, `[tool.pyright*]`) shall be locked, so dependency changes stay possible. The file is read as TOML statements: strings, multi-line strings, comments, and open brackets are tracked, so a statement keeps every line of a multi-line value and a `[` inside a string is not a header; a statement is locked when its full key (table plus dotted key, quoted keys decoded as TOML decodes them, spaces allowed) reaches a locked tool or the bare `tool` table. A header or key that does not read as TOML is locked, and so is everything under such a header (fail closed) (BUI-1201).
- **REQ-PROJ-5** Keel's own test suite shall prove the gate (red proof pass and fail) on JavaScript, Python/pytest, and Go fixtures. Where the `CI` environment variable is set, a missing Python/pytest or Go toolchain shall fail these tests instead of skipping them, so CI cannot pass without the proof.
- **REQ-PROJ-9** Globs (`testGlobs`, `verificationPaths`, `protected`, `bypassAllow`, `allowEdits`, `paths`) shall match the same on every platform, with `src/glob.js`: `*` and `?` stay in one segment, `**` spans segments, `[...]` classes and `{a,b}` alternatives work, a wildcard never matches a leading dot, and letter case counts in literal and wildcard parts alike (REQ-GATE-4 folds only the locks, by lowercasing both sides). Glob syntax it does not read (extglobs, POSIX classes, brace ranges) shall fail visibly. Rationale: on 2026-10-13 Node's `path.matchesGlob` matched the wildcard parts without regard to case on macOS only, so `Latest.java` was an existing `**/*Test.java` test on a Mac and not in Linux CI (BUI-1211).

Traceability (V-model, checked by machine)

- **REQ-CLEAN-3** Each `keel poll` pass and each `keel run` start shall first remove, across every repo, each parked worktree under the state dir that is safe and finished, with its branch, the way `keel clean --force` does (REQ-CLEAN-2). Safe: its HEAD is its own `keel/<card id>` branch, no live run holds its run lock (REQ-RUN-10), it has no uncommitted change (tracked or untracked), and every commit on it that no other branch outside `keel/*` and no remote-tracking ref holds is a Keel commit `chore(<card id>): keel attempt <n> leftovers` (REQ-RUN-7). Finished: no commit is only there (its tip is in the base or another branch, or was pushed; a merged PR's branch stays in its remote-tracking ref), or the card's last activity (its newest ledger row in that repo, else the tip's commit time) is more than `worktreeKeepDays` days old (keel.json of the owning repo at HEAD: an integer ≥ 0, default 7). Nothing younger than one hour is removed, so a run that just ended is left to its own poll. It logs `removed <path> (<why>)`. Rationale: on 2026-10-14, 31 parked worktrees had piled up across 8 repos (BUI-1253); a kept worktree also stops a retry of its card with `worktree exists`.
- **REQ-CLEAN-4** The cleanup shall never remove a worktree that is not safe (REQ-CLEAN-3): it logs `kept <path>: <reason>` (uncommitted changes; commits only there that Keel did not make; on another branch or a detached HEAD; a keel.json it cannot read; a git error), once per path and reason: the reported pairs are kept in `cleanup-kept.json` in the state dir, and a path is reported again only when its reason changes. A failure on one worktree never stops the cleanup, the poll, or the run.
- **REQ-CLEAN-5** The cleanup shall also remove gate checkouts that no live process owns: a checkout is named `keel-wt-<pid>-<random>` after the gate that made it (REQ-GATE-34), and one whose pid is dead is removed; a checkout of the earlier name `keel-wt-<random>` is removed when it is more than a day old (no gate lives that long). It looks only at directories with those names in `TMPDIR/keel.noindex` and in `TMPDIR` itself (from before REQ-GATE-34), removes only that exact path, never follows a symlink, and then runs `git worktree prune` in the repo the checkout's `.git` file names. Rationale: a killed gate never reaches its `finally`; 6,343 `keel-wt-*` checkouts were left in TMPDIR on 2026-10-14.
- **REQ-TRACE-1** Every requirement ID in §5 shall be unique and shall have at least one test whose title starts with that ID, and every test title shall start with a §5 requirement ID.
- **REQ-TRACE-2** The module table in §6.1a shall list exactly the files in `src/` and `bin/`, so the architecture description cannot drift from the code.
- **REQ-TRACE-3** The documentation set shall stay small (G6): `docs/` holds only `DESIGN.md`, `PILOT.md`, and `UNATTENDED.md`. (The 800-line cap was removed 2026-10-10: a line count is not a quality measure.)
- **REQ-TRACE-4** Under `npm test`, `claude` and `codex` on `PATH` shall be stand-ins in `test/bin` that fail at once (exit 97), so no test can reach a real model CLI or spend a provider window. Rationale: a CLI gate test with review on started a real Codex review on every `npm test` and drained the shared Codex window on 2026-10-13 (BUI-1209).
- **REQ-TRACE-5** A test process shall leave no directory in `TMPDIR` when it exits, with any exit code: the test helper `tmp()` makes one `mkdtemp` parent per process, puts every temp dir inside it, and removes exactly that recorded parent on process exit. Rationale: `tmp()` dirs were never removed, and on 2026-10-14 `TMPDIR` held about 3,500 `keel-*` dirs that Spotlight indexed (BUI-1214).

Autonomous loop (Linear)

- **REQ-LINEAR-1** `keel poll` shall list open issues in the configured Linear project, ordered by priority then age, and select the first one not already recorded as attempted in the ledger for this repo.
- **REQ-LINEAR-2** Keel shall derive a card from the selected issue: `kind` from its labels and title (REQ-LINEAR-24), `size` from its estimate (no estimate → `S`), `id`/title from the issue identifier and title, and the issue description as the requirements body. If the issue has no description, `keel poll` shall skip it and record why, rather than run an empty card.
- **REQ-LINEAR-3** If the derived card is missing a required field the gate would reject (e.g. an unmapped label), or the issue's own description says it is blocked by something outside the codebase (account/billing/vendor condition — a heuristic phrase match, found from the live pilot's BUI-669), then `keel poll` shall skip the issue, comment the reason on it, and move to the next issue rather than run an invalid or unfixable card.
- **REQ-LINEAR-4** After a `keel run` reaches a decision, Keel shall post exactly one comment on the issue: on pass, the branch name (and PR URL if `--pr`) and which tier passed; on failure, the trimmed final failure summary and the worktree path.
- **REQ-LINEAR-5** When `keel run` passes and is not `needsReview`, `keel poll` shall comment and move the issue to its team's review state (REQ-LINEAR-13); it never moves an issue to Done itself, except an issue proven already done (REQ-LINEAR-30). When it passes but `needsReview` (protected/L/infra), it shall comment but leave the issue's state unchanged for a human decision. On failure it shall leave the issue open. (Amended 2026-09-30: it used to move a passing issue to Done; two live runs showed a gate pass is not review.)
- **REQ-LINEAR-6** `keel poll` shall record one ledger row per issue attempted (issue id, outcome, timestamp) so a repeated poll does not re-attempt an issue already decided in this run of the loop, and so `keel report` can show issues closed autonomously. When reporting a run to Linear fails after the run, the poll records the attempt (`reportFailed`, or `deferred` for a transient stop) before it fails visibly, so the next poll does not pay to build it again; the run's follow-ups are queued before any Linear call.
- **REQ-LINEAR-7** `keel poll` shall take a Linear client as an injected dependency; the default client calls Linear's own HTTP API with `LINEAR_API_KEY` (`keel poll` is a plain CLI subprocess, not an agent session — it has no MCP access, the same reason worker CLIs are shelled out to rather than called in-process). Tests use a fake client, so the loop is testable without a live Linear connection or key.
- **REQ-LINEAR-8** `keel poll --limit N` shall stop after N issues are attempted (pass or fail counts; skipped issues do not) in one invocation; the default is 1. N that is not a positive integer is a usage error (exit 2), as for `keel audit`: `abc` once ran nothing and exited 0.
- **REQ-LINEAR-10** `keel.json` may set `linearProject` (a non-empty string; default none). `keel poll` shall use `--project` when given (it must equal `linearProject` when that is set, REQ-LINEAR-34), else `linearProject`; with neither it shall fail as a usage error naming both. This lets each repo declare its own Linear project, so a schedule is `keel poll --repo <dir>` with no external mapping.
- **REQ-LINEAR-34** When `--project` is given and the repo's `keel.json` sets a different `linearProject`, `keel poll` shall fail as a usage error that names both projects and the repo path, before it calls Linear or creates a worktree. Rationale: `keel poll --project keel --issue BUI-1325` run from another product's checkout built the keel card in that repo, paid a tier, commented "blocked", and left a stray worktree (2026-10-16, BUI-1342).
- **REQ-LINEAR-35** When `--project` equals `linearProject`, or `keel.json` sets no `linearProject`, `keel poll` shall use `--project` as REQ-LINEAR-10 states.
- **REQ-LINEAR-11** `keel poll` shall never pick, comment on, or record an issue that carries the label `no-keel` (case-insensitive) in any position. This is the owner's opt-out for tracking, umbrella, and decision issues that are not code cards.
- **REQ-LINEAR-12** An issue description may contain a fenced code block labelled `keel` holding card header lines (`kind`, `size`, `paths`, `allowEdits`, `heldOut`). `keel poll` shall apply them over the derived `kind` and `size`, remove the block from the requirements text, and reject the card on an unknown key (REQ-CARD-2) so the issue is skipped with a reason. Trust: the block can widen what a worker may change, so it is exactly as trusted as whoever can edit the issue (a single-owner workspace today).
- **REQ-LINEAR-13** The review state for a passing issue is the team's first `started`-type state whose name matches `/review/i`, else its first `started`-type state; with no started-type state the poll shall fail visibly rather than close the issue. Done is reached by a human or by the merge of a PR that names the issue (`Closes <ID>`). The poll outcome for such an issue is `inReview`.
- **REQ-LINEAR-14** `keel poll --issue <ID>` shall run exactly that open issue, even if a previous poll already decided it (an explicit human retry; the ledger still records the new attempt, with the outcome's own detail and `byHand: true`, so a NEEDS_HUMAN question or SPLIT child IDs (REQ-LINEAR-33) are kept; amended 2026-10-17, BUI-1288: the detail used to be overwritten with `explicit --issue retry`). `<ID>` must match `[A-Z]+-[0-9]+`, else a usage error. It never overrides the `no-keel` label (REQ-LINEAR-11), an invalid card raises its reason instead of skipping silently, and an ID not among the open issues runs nothing and comments nowhere. `--limit` does not apply.
- **REQ-LINEAR-15** When a run stops `blocked` (REQ-RUN-13), `keel poll` shall post one comment that names the worker's reason and the worktree, leave the issue's state unchanged, record the outcome `blocked`, and exit 1. The comment tells the owner to fix the card or repo and retry with `--issue`.
- **REQ-LINEAR-16** After a run and before commenting or moving the issue, `keel poll` shall read the issue's current state. If it is completed or canceled (closed by a human or another session while Keel ran), Keel shall post one comment naming its branch, leave the state unchanged, and record the outcome `closedMeanwhile`. Rationale: on 2026-10-04 a poll moved BUI-1028 from Done back to In Review a minute after another session merged its fix.
- **REQ-LINEAR-18** When a run passes but its PR step fails (push rejected by a hook, `gh` error), `keel poll` shall post one comment with the error and the certified branch and worktree, leave the issue's state unchanged, record the outcome `prFailed`, and exit 1. Rationale: on 2026-10-07 BUI-1074 passed the gate, a pre-push test timeout rejected the push, and the poll reported `inReview` with no PR.
- **REQ-LINEAR-19** When a run stops for a provider reason (`quota`, `review-unavailable`), `keel poll` shall remove its clean worktree and branch (except a `pendingReview` build, REQ-RUN-24, which it keeps and names in the comment), post one comment that the card is deferred, record the outcome `deferred`, which does not count as attempted (REQ-LINEAR-6), and exit 3. The next poll retries the issue; the same poll does not pick it again and goes on to the next issue. Rationale: on 2026-10-07 the Codex reviewer hit its usage limit; before this, such a card was recorded as attempted and never picked again.
- **REQ-LINEAR-20** An issue that an open issue still blocks (a Linear `blocks` relation whose blocker is not completed or canceled) shall wait: `keel poll` shall not pick, comment on, or record it, and shall log `<ID> waits for <blockers>`; once every blocker is closed it is eligible again. `--issue` (an explicit human retry) does not check blockers. Rationale: the `cards` skill writes dependent slices with `blocks` relations; picking by priority alone built a slice before the one it needs, so the dependency graph now sets the build order.
- **REQ-LINEAR-22** After every run, deferred included, `keel poll` shall queue its follow-ups in the poll ledger (`found`) and then, at the start of a poll and after each run, file each queued follow-up, oldest first, (REQ-RUN-26, -27) as a new issue in the source issue's team and project (an item with no source: the polled project and its first team; a project name that does not match exactly one project is a filing error), priority Low; no source, no source comment. Its description is a card in the skills/cards format, so the loop builds it without a refine turn (REQ-LINEAR-32): one to three lines of context (`Found by keel while building <source>.` or `Found by keel.`, then the commit the work is about and the run's PR, or the audited PR); `## Problem` with the title and detail and, when REQ-LINEAR-27 stored it, the quoted cited line; `## Requirements` with one EARS line ("When …, the … shall …"); `## Acceptance` with one checkbox naming the test that proves it (a new test that fails before the change; for a `chore`, new tests in a new test file); and a `keel` block (REQ-LINEAR-12) with `kind:`, `size: S`, `paths:` when the finding cites a path (its directory, the test globs that cover the repo's test files at base, and `**/*.md`), and `allowEdits:` where REQ-LINEAR-29 applies. A title that an open issue in the project already has, or one completed or canceled in the last 30 days (case-insensitive, trimmed as Linear stores titles), is marked `dup`, not filed: work fixed by hand or declined is not filed again. It files at most `followUpsPerDay` (keel.json: an integer ≥ 0, default 5, 0 = off) per repo per UTC day, counted from `filed` rows in the poll ledger; the rest waits in the queue for a later day. Queued items are distinct by title (case-insensitive; the first source wins). An item leaves the queue when its issue is created, marked `dup`, or after 3 failed tries (`file-error` rows; the third comments the error on the source issue), so a failed Linear call loses nothing and one bad item cannot block the queue. Leaving settles only the work queued before it: the same title found again later is queued again, and the dedupe above decides (a title once filed was otherwise never filed again, with no row or log). Filed issues are not attempts (REQ-LINEAR-6), so a later poll builds them. One comment on the source issue lists the new IDs. A filing error, including a failed comment on the source issue, never stops a poll: the source comment says what was filed, the poll result gets `followUpsFailed` with the error, and the poll exits 1. Trust: the text is model-written; it reaches only a builder prompt, never a shell, and the gate still decides.
- **REQ-LINEAR-23** At the start of each poll, in a repo with an `origin` remote, `keel poll` shall list open PRs with `gh`. For each on a `keel/<ID>` branch that GitHub reports `CONFLICTING`, it shall close the PR with a comment and `--delete-branch` (GitHub keeps its commits), remove the branch's clean worktree or local branch, comment on the issue, and record the issue `deferred`, so this poll builds it again on the current base. A worktree with uncommitted changes is left as is, with a log line. A `gh` failure skips the check with a log line. An issue's latest poll outcome decides whether it counts as attempted (REQ-LINEAR-6), so `deferred` after an earlier outcome makes it eligible again. Rationale: on 2026-10-12 PR #117 conflicted after #116 merged, and its auto-merge would have waited forever.
- **REQ-LINEAR-24** The kind of an issue's card shall come from any of its labels, not only the first: a `Bug` label makes it `bug`, else a `Feature` or `Improvement` label makes it `feature`. An unlabeled issue whose title describes a failure (a `fix:` prefix, or a word such as fails, broken, crash, hangs, leaks, wrong, misses, lost, regression, ignores, drops, skips) is a `bug`; a `docs:`, `chore:`, `style:`, `build:`, or `ci:` title, or any other, is a `chore`. A `keel` block's `kind` (REQ-LINEAR-12) still wins. Rationale: a chore skips red proof and held-out tests, and two of the three real escapes found on 2026-10-14 had run as chores; issues filed by agents carry no labels, so before this every one of them ran as a chore.
- **REQ-LINEAR-25** `keel poll` shall not pick an issue whose text marks it as human work, not a code task: a title with `decide` or `make the … decision`, or a description line that starts `Decision for` / `Decision needed` / `Decision required` (a decision); a title with `playtest` (a playtest); a title with `umbrella`, `epic`, or `tracking issue`, or a description with `all child issues complete` (or sub-issues, done, closed) (an umbrella); a title or description with `operator step`, `manual step`, or `runtime-only`, or a description line that starts `No code change` (an operator step). Case is ignored. It posts one comment that names the category and the matched text and says how to opt back in (a `keel` block, REQ-LINEAR-12, or `--issue`), and records the outcome `notKeel`, so it is not picked or commented on again while its text still reads as human work, and the human touch rate leaves it out (REQ-LED-16). An issue with a `keel` block is a card by intent and is not triaged: when a `notKeel` issue later gains one (or its text no longer matches), the next poll picks it like any unattempted issue, and the outcome of that build is its new attempt (amended 2026-10-17, BUI-1352: the comment advertised the `keel` block, but the `notKeel` row kept the issue out for good); `--issue` (REQ-LINEAR-14) does not triage. Rationale: 7 of the runs that stopped for a human in October were such issues (BUI-1129 a decision, BUI-535 and 541 playtests, BUI-689 an umbrella, BUI-1155 an operator step); each paid a model to say so.
- **REQ-LINEAR-26** An issue whose title or description names a prerequisite issue (`needs`, `requires`, `after`, `once`, `depends on`, `blocked on` or `by`, `waits for` or `on`, or `until`, then within 60 characters of the same sentence an identifier `[A-Z][A-Z0-9]*-[0-9]+`) shall wait like a `blocks` relation (REQ-LINEAR-20) while that issue is open: listed among the open issues, or, outside the project, its state (read once per poll) is not completed or canceled. The issue itself and the source line `Found by keel while building <ID>` (REQ-LINEAR-22) are not prerequisites. An identifier Linear cannot read is logged (`prerequisite <ID> of <issue> not read: <reason>`) and not waited on. `--issue` does not check prerequisites. Rationale: BUI-1163 (`once example-app BUI-1133 ships`) and BUI-1164 (`after the … decision (BUI-1129)`) were built before their prerequisite and stopped for a human.
- **REQ-LINEAR-27** Re-check before filing: when it queues found work (REQ-LINEAR-22), Keel shall record, for each item that cites a `path:line` (in its detail, else its title) that exists in the commit the work is about (the run's branch; for `keel audit`, the merged commit), that line's trimmed text and the commit as `cite`. A path may hold spaces (`.github/workflows/quality gate.yml:3`): the cited path is the longest one, of the match and up to 8 words before it joined by single spaces, that is a file in that commit (amended 2026-10-18, BUI-1387). Before filing a queued item with a `cite`, if the cited line was there before the finding's own work (it is in the file at the merge base of the cited commit and the poll's base) and the file is gone from the base, or no line of the base's file has that text any more, the poll shall not file it: it records a `stale` row with the reason in the poll ledger, logs it, and the item leaves the queue. A line that the finding's own unmerged branch added is never judged stale. For an audit finding the merge base is the merged commit, so it is compared with the base HEAD. Rationale: two audit issues (BUI-1219, BUI-1247) were already fixed on main when built, and the builder could only report them satisfied.
- **REQ-LINEAR-28** A follow-up whose source issue is still open (not completed or canceled) shall be filed with a `blocks` relation from the source to it (`blockedBy: [source]`; the HTTP client adds it with `issueRelationCreate` after the issue is created), so REQ-LINEAR-20 makes it wait until the source closes. When the relation fails, the client deletes the new issue and the filing fails (REQ-LINEAR-22 `file-error`), so a retry files it whole instead of deduping an unlinked issue. A closed source, or none, adds no relation. Rationale: follow-ups of unmerged work (BUI-1163, BUI-1164 needed BUI-1130) were built before their source and blocked.
- **REQ-LINEAR-29** When the path a follow-up cites is one the gate locks (`verificationPaths`, matched as the gate matches it, REQ-GATE-4), the filed issue's `keel` block shall carry `allowEdits: <that path>` after `kind:`, and its `## Requirements` shall say, under the EARS line, the edit must not remove or weaken any check, job, or test step. The gate's other protections still apply. Rationale: three audit issues (BUI-1217, BUI-1225, BUI-1230) needed `.github/workflows/quality.yml` and blocked because the card did not allow the edit.
- **REQ-LINEAR-30** The builder prompt shall tell the worker that when the card is already satisfied by the current code, it writes `KEEL_DONE` (not `KEEL_BLOCKED`) with the commit SHA or PR number that satisfied it. Keel removes `KEEL_DONE` like `KEEL_BLOCKED` (REQ-RUN-13) and stops `blocked` with the reason prefixed `already satisfied:`. When a poll run stops `blocked` with a reason that says `already satisfied` (either file), `keel poll` shall verify the evidence: each `commit <sha>` the reason names must be an ancestor of the poll base, and each `PR #N` or `(#N)` it names is looked up with `gh pr view`; evidence holds when at least one named commit is on base or one named PR is `MERGED`, and no named commit is missing from base. It then runs install, every configured check, and the test command on a clean checkout of base, as `keel doctor` does (REQ-CLI-3); acceptance commands are informational there and not required. When evidence and checks hold, it moves the issue to its team's first `completed`-type state, then posts one comment citing the evidence and the green checks with the base SHA, and records the outcome `alreadyDone`; when the move fails, it posts no such comment but one that says the issue stays open and why, and the error goes on (REQ-LINEAR-6) (BUI-1380: the comment used to come first and claimed a close that failed); this is the one case where Keel moves an issue to Done (amends REQ-LINEAR-5). Otherwise it is a `blocked` stop (REQ-LINEAR-15) whose comment adds why the evidence did not hold. Rationale: BUI-1018 (`already satisfied … PR #546 (commit 4616da6)`), 1219, and 1247 each waited for a human to close an issue the worker had proven done.
- **REQ-LINEAR-31** `keel poll --file-only` shall file the queued follow-ups (REQ-LINEAR-22) and exit, building, commenting on, and recording no issue; it exits 1 on a filing error, else 0. With `--issue` it is a usage error. Rationale: repos without a nightly builder still file their nightly audit findings (REQ-CLI-11).
- **REQ-LINEAR-32** Refine before build: where `refineIssues` is true (keel.json, default `true`, validated as a boolean), when `keel poll` (also `--issue`) is about to build an issue that is not buildable — no testable requirement (no line with `shall` and no Acceptance checkbox `- [ ]`), or obviously too big (estimate over 5, more than 8 `shall` lines, or over 8000 characters) — Keel shall first run one refine turn: the start tier of the issue's card (REQ-RUN-2), on a temporary checkout of base that is removed afterwards, with a prompt (`src/refine.js`, the skills/cards format embedded) that gives the issue, `keel.json` at base, and says the turn is read-only. It skips the turn when the description has a `keel` block, `## Requirements`, and `## Acceptance` (Keel's own follow-ups, REQ-LINEAR-22, always do), or a `## Refined by keel` heading. Tests that inject `runFn` inject the turn as `refineFn` too. Rationale: of 46 builder-blocked runs, 7 were contradictory or infeasible, 6 already done, and many vague; a cheap turn that clarifies, proves done, splits, or asks one question costs less than a blocked tier ladder and a vague human stop.
- **REQ-LINEAR-33** The refine turn's reply shall be parsed strictly: its first line (a trailing exec result JSON line is ignored) is one of `CARD`, `ALREADY_DONE <commit <sha>|PR #n>`, `SPLIT`, `NEEDS_HUMAN <question>`. Keel posts one issue comment with the result. (a) `CARD` then a card with a `shall` line under `## Requirements` and an open checkbox `- [ ]` under `## Acceptance` (each section runs to the next heading or code fence; a `shall` or checkbox elsewhere, or a checked `[x]`, does not count), and a `keel` block with `kind`, `size` S or M, and `paths` that maps to a valid card, and that does not loosen the issue's policy (the issue text is untrusted and the card builds unattended: a `bug` or `feature` issue keeps kind `bug` or `feature`, and `allowEdits` may only repeat paths the issue's own `keel` block allows): Keel writes the description as `## Refined by keel`, the card, then `## Original description` and the original text, records `refined` (not an attempt), and builds it; when the refined card's `paths` cover a file an open branch changes, it waits for the lease unrecorded and uses no `--limit` slot, so the poll picks the next issue (REQ-LEASE-3). (b) `ALREADY_DONE`: the REQ-LINEAR-30 verification; when it holds, Keel comments the evidence, closes the issue, and records `alreadyDone`; otherwise it comments why and builds the issue as written. (c) `SPLIT` then 2 to 5 cards, each `TITLE: <title>` and a card as in (a): Keel files them in order as sub-issues of the issue (`parent`, the issue's priority unchanged, Linear's `0` (no priority) included (BUI-1289), each `blockedBy` the one before), records `split` with the new IDs (also when a later Linear call fails, so the next poll does not split it again), and builds none this pass. (d) `NEEDS_HUMAN` with a question: Keel comments the question, records `needsHuman` with it, builds nothing, and the poll exits 1; the human touch rate counts it as a stop for a decision (REQ-LED-14, -16). Any other reply, or a worker that does not end `ok`, is a visible failure: a log line and a comment with the reason, then the issue is built as written. The HTTP client adds `parentId` (the parent's UUID) and `setDescription`.
- **REQ-LEASE-1** Path leases: the files each other open branch of the repo changes are leased to it. Open branches are the `keel/*` branches whose `keel run` is in progress (a worktree in `git worktree list` under the state dir whose run lock, REQ-RUN-10, holds a live pid), with their diff from the merge base plus their worktree's uncommitted and untracked files, and, with an `origin` remote, the open PRs `gh pr list` returns with their files; the branch being built or gated is never one of them, also as a PR. A `keel/*` branch with no run in progress and no open PR is not open: Keel squash-merges, so a merged branch never becomes an ancestor of base, and a failed run's branch stays until `keel clean`. Prose files (`.md`, `.txt`, `.rst`) are shared and never conflict. A `gh` failure prints `path lease: open PRs not checked: …` and only local branches are checked. Before it gates, `keel gate` shall print, and not block, `WARN paths overlap <branch> (<files>): merge one first, then rebase the other` for each open branch that changes a file HEAD changes. Rationale: 12 parallel branches of one product repo changed the same files; six conflicted at merge and each gated again for 20–40 minutes (BUI-1183).
- **REQ-LEASE-2** `keel run <card.md>` shall not start a card whose `paths` cover a file an open branch changes (REQ-LEASE-1); it prints `path lease: <card> overlaps <branch> (<files>), …; merge or close it first, or narrow the card's paths` and exits 3 without creating a branch. A card without `paths` leases nothing.
- **REQ-LEASE-3** `keel poll` shall pass over an issue whose card `paths` cover a file an open branch changes: it logs `<ID> waits for path lease: <branch> (<files>), …`, does not comment on or record it (it is not an attempt), and picks the next issue; a later poll builds it once those branches merge or close. `keel run <ISSUE-ID>` (`--issue`) on such an issue does not start it and exits 3 (outcome `leased`).
- **REQ-LINEAR-9** `keel.json` may set `dailyBudgetUsd` (a positive number; default none = no ceiling). Each ledger row records the `repo` it ran in. Before each issue, `keel poll` shall sum the estimated `cost` of today's (UTC) ledger rows for this repo; if that sum is at or above the ceiling it shall stop, run nothing, comment on no issue, log the spend and ceiling, and exit 3. Rows without cost data (e.g. Codex) cannot be priced: they are counted and logged as unpriced, never treated as zero silently.

## 6. Architecture

Keel has two parts. The **gate** is language-free: it knows git, file globs,
and commands. The **runner** drives any agent CLI and uses the gate result to
choose the next model. Everything project-specific lives in `keel.json`.

```
                    keel.json (at base: commands, globs, locks, tiers)
                               │
card.md ──▶ keel run ──▶ worktree keel/<id> ──▶ worker CLI (tier N: model + effort)
                │                                   claude -p | codex exec | any exec
                ├─▶ commit leftovers, must stay on branch
                ├─▶ keel gate (fresh checkouts of base and head)
                │      static: locks, markers, scope
                │      head:   project checks + regression tests
                │      base:   red proof, held-out must fail
                │      ──▶ receipt.json
                │   pass ─▶ branch / PR of the certified SHA   fail ─▶ tier N+1 with failure summary
                └─▶ ledger.jsonl ──▶ keel report
keel init ──▶ detects the project ──▶ proposed keel.json (you review and commit it)
```

### 6.1 Project contract

Keel needs only this from a project, whatever its language or type:

| Keel needs                                                                                   | Where it comes from                       |
| -------------------------------------------------------------------------------------------- | ----------------------------------------- |
| A git repo                                                                                   | —                                         |
| `checks`: commands that exit 0 when the project is healthy (lint, types, build, tests, plan) | `keel.json` (proposed by `keel init`)     |
| `testCommand`: runs the tests; non-zero when a test fails                                    | `keel.json`                               |
| `testFilesCommand` (optional): `testCommand` for given `{files}` (REQ-GATE-33)               | `keel.json` (proposed by `keel init`)     |
| `testGlobs`: which files are tests                                                           | defaults cover common languages           |
| `verificationPaths`: files that define "passing"                                             | defaults cover common runners and tools   |
| `shareDirs` (optional): dependency dirs to link into temp checkouts (REQ-GATE-48, 49)        | defaults: `node_modules`, `.venv`, `venv` |
| `mutation` (optional): mutation-test command over `KEEL_CHANGED_FILES` (REQ-GATE-20)         | `keel.json`                               |

`keel init` presets (a starting point; you review the file):

| Marker                                                                                 | Proposed checks                                         | testCommand                          |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------ |
| `package.json` (+ lockfile → npm/pnpm/yarn/bun)                                        | scripts `lint`, `typecheck`, `build`, `test` that exist | `<pm> test`                          |
| `pyproject.toml` / `requirements.txt` (uv.lock → `uv run`, poetry.lock → `poetry run`) | `ruff check .`, `mypy .` when configured; tests         | `<runner> python -m pytest -q`       |
| `go.mod`                                                                               | `go vet ./...`, tests                                   | `go test ./...`                      |
| `Cargo.toml`                                                                           | `cargo clippy -- -D warnings`, tests                    | `cargo test`                         |
| `Gemfile`                                                                              | `bundle exec rubocop` when configured; tests            | `bundle exec rspec` (or `rake test`) |
| `Makefile` with `test:`                                                                | `make lint` if present; tests                           | `make test`                          |
| `*.tf` at root                                                                         | `terraform fmt -check`, `terraform validate`            | — (infra: set a plan check)          |

Other stacks (Java, .NET, PHP, docs sites, mobile) work by writing the

### 6.4 Human touchpoints

1. Writing the card (requirements) — or approving one drafted by an agent.
2. Merging PRs for `infra`, protected paths, or `size: L` whose held-out tests did not pass (REQ-RUN-20; authored by default, REQ-RUN-28).
3. Parked cards (all attempts failed).
4. Deploy, publish, send, spend: never done by Keel.

### 6.4a Daily workflow

1. Once per repo: `keel init` → review and commit `keel.json` on the default branch (policy lives at base).
2. Your own change: commit on a feature branch, then `keel gate` before the PR (base and card default, REQ-CLI-6, 7). Write a card only to set scope, size, or held-out tests; keep it outside the repo or commit it to base first (REQ-CARD-3).
3. A change for Keel to build: `keel run BUI-123` (a Linear issue, REQ-CLI-8) or `keel run <card>` → Keel builds, gates, escalates; you get a branch (or PR with `--pr`) of the certified commit. `keel poll --limit N --merge` works the backlog.
4. Review and merge. `keel report` shows cost per accepted card.

### 6.4b Linear loop

```
keel poll --project <name> [--repo <dir>] [--limit N]
        │
        ▼
list open Bug/Feature/Improvement issues, unassigned to a Keel run, priority order
        │
        ▼
pick the first one Keel hasn't already attempted and no open issue blocks
        │
        ▼
map issue → card (kind from label, size from estimate, title, description as requirements)
        │
        ▼
unclear or too big? one read-only refine turn: CARD → build it, ALREADY_DONE → verify and close,
SPLIT → file sub-issues, NEEDS_HUMAN → ask one question (REQ-LINEAR-32, -33)
        │
        ▼
keel run  ──▶ pass ──▶ comment the branch/PR on the issue, move it to review, move on
              │
              └─▶ fail ──▶ comment the failure summary on the issue, leave it open, move on
```

Linear is called through an injected client (REQ-LINEAR-7): `src/linear-http.js`
calls Linear's HTTP API with `LINEAR_API_KEY`, because `keel poll` is a plain
subprocess with no MCP access; tests use a fake client.
Keel's core (`gate.js`, `run.js`) has no Linear dependency — `poll.js` is the
only module that imports it, so the gate/runner stay usable with zero
dependencies for anyone who doesn't use Linear.

`keel poll` is not a background daemon (v1): each invocation does one pass
(pick, run, report, exit) so it can be driven by cron/launchd or by hand
without new process-supervision code.

### 6.5 Trust model and security

- Trusted: the card (human-written), the base commit (config from `keel.json`
  at base), Keel itself. Untrusted: everything in base..head.
- Verification files (tests at base, runner configs, `keel.json`, CI,
  `package.json` scripts) are locked unless the card's `allowEdits` names them.
- Keel is not a sandbox. Worktrees are not isolation. Workers and checks run
  with the invoking user's rights. Run Keel locally from a shell without
  production secrets. A CI gate that executes candidate code must run in an
  isolated, secret-free job with a trusted workflow definition.
- No card text reaches a shell: git and gh are called with argument arrays;
  card IDs are validated.
- Subscriptions: local use of the unmodified `claude` / `codex` CLIs under the
  user's own login. Keel never reads or stores credentials. OpenAI directs
  programmatic CI use to API-key auth, so CI runs only the gate (no model).
  "Free" means no extra bill within existing plans; plan limits still apply.

### 6.6 Known limits

- Red proof is counterfactual ("fails before, passes after"), not proof of
  test-first order or of failing for the right reason. The "names a new test
  file" check is a heuristic. Mitigations: held-out tests for M/L, human spot
  check, the optional `mutation` stage (REQ-GATE-20).
- Authored held-out tests (REQ-RUN-17) can assume names the card does not give; the builder gets only "details
  withheld", so such a card fails all attempts. Fix the card's interface text or write the tests by hand.
- The post-deploy workflow (REQ-PROJ-8) recovers by revert, so production serves the bad deploy until CI and a
  build finish; without `KEEL_BOT_TOKEN` the revert PR waits for a human, since CI does not start on it.
- Skip/bypass scans are line heuristics.
- Temp checkouts share `node_modules`/`.venv` by writable symlink.
- Test identity is by glob, not by the runner's collected test list.

## 8. How Keel's value is judged

The matched pilot (16 pairs, `docs/PILOT.md`) is closed: Keel accepted 16/16 with no review defect against 14/16
and 2 defects for plain Claude Code, at $0.10–0.80 per card.

SWE-bench Verified (30 tasks, 2026-10-13, `bench/swebench/README.md`): Keel 28/30 resolved at $8.95, plain Claude
Code 25/30 at $10.36; the deterministic gate caught 35/35 tampering cases.

Since then Keel is judged on real use, against the owner's own baseline, not an absolute bar:
`keel report --value` (REQ-LED-8) compares how often Keel merges and other changes in the same repos are later
fixed or reverted, and prints finished cards, the human touch rate (REQ-LED-14), and builder and review tokens and cost per
finished card (REQ-LED-13). Speed is in `keel report --dora`
(REQ-LED-7). On 2026-10-10 (77 runs, 14 repos): Keel merges 2/30 later fixed or reverted (7 %), other changes
52/150 (35 %); 51/77 runs accepted; ≥ $0.98 per accepted card. Those shares were file-level; since
2026-10-14 a fix counts only when it changes lines the merge wrote, docs left out (REQ-LED-10).

Economics: cheapest-first saves only if cheap cost L < p × H (p = cheap pass rate, H = strong cost).

## 9. v2 plan: the autonomous loop (owner, 2026-10-07)

Goal: a Linear issue reaches verified production with no human step, and every step leaves evidence. Owner rule:
auto-merge is allowed when the change is tested and reviewed. Keel stays the referee (§4): CLIs build and review,
launchd or Routines trigger, GitHub auto-merges after required CI, Vercel deploys, product CI verifies production.

Merge policy: Keel merges only with `--merge`, and only a gate-certified SHA with every check green. `--merge` enables
auto-merge only after the gate passes, review included, and after the `keel/gate` status is on the certified SHA
(REQ-RUN-23). Require `keel/gate` on the default branch so a later push cannot merge. A protected, `infra`, or L
change also needs passing held-out tests; otherwise Keel opens a draft PR labelled `needs-human`. Where GitHub
auto-merge is unavailable (no required checks, auto-merge off, or the call refused, as on a private repo of a free
account), `keel poll --merge` merges the certified SHA itself (REQ-MERGE-1..7): `--match-head-commit <sha>`, only
after every check run, commit status, and workflow run on it, `keel/gate` included, completed successfully, only
when GitHub reports the PR mergeable, never after a later push, and within `selfMergeTimeoutMinutes`; otherwise the
PR stays open with the reason on it and on the issue. Keel never deploys and never bypasses branch protection.
